# Templar Survivors — 설계 노트

중세 판타지 오토배틀 서바이벌. 이 문서는 프로토타입의 설계 근거와,
정식 개발로 넘어갈 때 결정해야 할 것들을 정리한다.

---

## 1. 현재 프로토타입 (`game/index.html`)

의존성 0, 파일 1개, 에셋 0개. 브라우저로 바로 열린다.

| 구현됨 | 내용 |
| --- | --- |
| 코어 루프 | 이동 → 자동 공격 → 경험치 → 레벨업 3택 → 강해짐 |
| 직업 | 성기사 / 전사 / 추적자 / 마법사 — 시작 무기 + 스탯 성향 + **고유 자원 + 능동 스킬** |
| 무기 8종 | 투척 단검 · 성역 · 쇠사슬 플레일 · 마법 화살 · 천벌의 번개 · 수호 성서 · 불꽃 파도 · 피의 낫 |
| 속성 6종 | 물리 · 화염 · 냉기 · 뇌전 · 신성 · 피 — 무기마다 하나씩 |
| 조합 6종 | 서로 다른 속성의 무기를 함께 들면 열리는 특수 효과 |
| 패시브 9종 | 힘 / 기도 / 신앙 / 신발 / 성갑옷 / 생명력 / 재생 / 자석 / 탐욕 |
| 적 8종 | 박쥐 · 슬라임 · 유령 · 좀비 · 거인 · 사신 · **사냥개** · 보스 |
| 웨이브 | 시간 스케일링, 30초 러시, 5·10·15분 보스, 7분 이후 사냥개 무리 |
| 메타 진행 | 영혼의 제단 — 판이 끝나도 남는 영구 강화 6종 |
| 성능 | 공간 해시 + 오브젝트 풀링 + 배칭 (적 340마리 기준 update 0.53ms/프레임) |

### 왜 이렇게 짰나

- **공간 해시(`SpatialHash`)**: 적 300마리 × 발사체 100개를 전수 비교하면 3만 번/프레임이다.
  70px 셀로 나눠 근처만 본다. 이 장르에서 성능은 나중에 고칠 수 없는 구조 문제라 처음부터 넣었다.
- **오브젝트 풀링**: 초당 수백 개의 파티클/발사체를 `new` 하면 GC가 끊긴다. 전부 미리 할당하고 `active` 플래그로 돌린다.
- **고정 타임스텝(1/60)**: 프레임률이 흔들려도 밸런스가 같게 나온다. 자동 밸런스 시뮬레이션도 이것 덕에 가능하다.
- **`draw`와 로직 분리**: 적/무기마다 그리기 함수가 분리돼 있어, 나중에 스프라이트로 갈아끼울 지점이 명확하다.

### 차별화 축 — 실제로 구현된 것

설계만 해두고 넘어가면 재미가 있는지 알 수 없어서, 두 축을 프로토타입에 넣었다.

**① 직업 자원 + 능동 스킬 (SPACE)**

자원이 차는 방식이 직업마다 달라서, 같은 맵을 4번 해도 플레이 리듬이 갈린다.

| 직업 | 자원 | 차는 방식 | 스킬 |
| --- | --- | --- | --- |
| 성기사 | 신앙 | **피격당할 때** 충전 | 심판의 빛 — 광역 정화 + 무적 |
| 전사 | 분노 | **처치할수록** 충전, 가만있으면 감소 | 광전사의 돌진 — 경로 관통 |
| 추적자 | 집중 | **안 맞은 시간**에 비례, 맞으면 0 | 그림자 도약 — 순간이동 + 단검 방사 |
| 마법사 | 마나 | 시간에 따라 일정하게 | 비전 폭발 — 유도 마력탄 난사 |

성기사는 위기가 곧 기회, 전사는 몰아쳐야 유지, 추적자는 무피격이 보상, 마법사는 자원 관리.
"언제 쓰느냐"의 판단이 생기면서 순수 오토배틀에 실력 차가 들어온다.

**①-b 자세(stance) — 직업마다 위치 선정 규칙이 다르다**

①만으로는 부족했다. 플레이테스트에서 "4직업이 솔직히 차이가 없다"는 피드백이 나왔고,
코드를 보니 원인이 그대로 있었다. `rollChoices()` 가 **`player.cls` 를 한 번도 참조하지 않았다.**
4직업이 완전히 같은 카드 풀에서 뽑고 있었던 것이다. 거기에 세 가지가 겹쳤다.

- 무기 8종 / 슬롯 6칸 → 레벨 12쯤이면 누구나 거의 같은 6종을 든다. 시작 무기 차이는 1/6로 희석
- 스탯 보정 ±8~20% → 패시브 한두 레벨보다 작아서 체감 불가
- 자원·스킬은 30초에 한 번 → 15분 중 30번. **나머지 시간의 플레이는 완전히 동일**

즉 직업이 "가끔 누르는 버튼"으로만 존재하고 매 순간의 플레이에는 없었다.
카드 종류를 늘리는 것(전용 무기 풀)으로는 이걸 못 고친다 —
카드가 달라져도 행동은 여전히 "카이팅하며 자동공격 구경"으로 같기 때문이다.

그래서 **위치 선정 규칙 자체를 정반대로** 만들었다. 기사와 마법사부터.

| | 기사 「진영」 | 마법사 「영창」 |
| --- | --- | --- |
| 규칙 | 멈추면 방벽(피해 -58%, 초당 회복), 곁의 적 1마리당 피해 +5% | 멈추면 영창 단계 상승, 단계마다 피해 +50% · 쿨다운 -18% |
| 풀리는 조건 | 움직이면 방벽 해제 | 움직이면 단계가 빠르게 빠진다 |
| 최적 행동 | **군중 한가운데로 파고들어 자리를 잡는다** | **거리를 벌리고 멈춘다** |
| 측정값 | 접전 ×14에서 피해 +98%, 피해 감소 58% | 4단계에서 피해 +200%, 쿨다운 ×0.28 |

같은 WASD인데 정반대 행동이 나온다. 화면도 완전히 달라진다 —
기사는 근접 난전, 마법사는 멀찍이 떨어진 룬 고리.

그리고 이 설계는 앞서 남겨둔 **"마법사 피격 0회"** 문제를 자동으로 해결한다.
멈춰야 강해지니 위험을 감수할 수밖에 없다.

**①-c 직업 전용 특성 카드**

자세를 강화하는 카드를 레벨업 풀에 섞고, **매 레벨업마다 전용 특성이 최소 1장 뜨도록 보장**했다.

- 기사: 강철 방벽 / 도발(적을 끌어당겨 더 둘러싸이게) / 성전(접전당 피해 증가) / 가시 갑옷(막은 피해 반사) / 불굴(저체력에서 강해짐)
- 마법사: 집중 영창 / 심층 마력(최대 단계 +1) / 잔류 마력(이동 중 1단계 유지) / 비전 과부하(3단계 이상 관통) / 마력 폭주(최대 단계 유지 시 주기적 폭발)

**도발**이 이 설계의 핵심이다 — 적을 끌어당기는 게 곧 피해 증가이므로,
"위험해 보이는 선택이 실은 최적"이라는 긴장이 생긴다.

**①-d 자세를 넣고 나서 드러난 두 가지 (봇 계측)**

봇을 직업별로 다르게 행동하게 만들고(기사는 파고들어 멈추고, 마법사는 벌리고 멈춘다)
다시 재보니, 각 자세가 성립하려면 반드시 있어야 하는 것들이 드러났다.

**기사 — 방어가 밀집도를 따라가지 않으면 자살 명령이 된다.**
처음엔 접전 스택이 *피해에만* 걸려 있었다. 결과는 3판 전패(5:45 / 6:46 / 10:17),
위험 구간 79~86%. "둘러싸일수록 강해진다"고 해놓고 둘러싸일수록 방어는 그대로였으니
파고들라는 설계가 그냥 죽으라는 뜻이었다.
→ **방벽의 피해 감소와 회복량도 접전 스택을 따라가게** 했다(최대 -80%).
결과: 2승 1패, 최저 HP 5~13%, 피격 146~216회. 아슬아슬하게 버티는 난전이 됐다.

**마법사 — 멈추면 경험치를 못 줍는다.**
자세를 넣자 피격이 0회에서 3~8회로 올랐다(의도한 대로 위험해졌다).
그런데 3판 전패였고 레벨이 5~16에 머물렀다. 원인은 화력이 아니라 성장이었다 —
**멈춰 있으면 보석을 주우러 갈 수 없다.**
→ 영창 단계에 비례해 **경험치 흡인 범위**가 커지도록 했다(단계당 +70%).
"멈춰라"가 "경험치를 포기해라"가 되면 직업 자체가 성립하지 않는다.

교훈 하나: **자세처럼 플레이 방식을 강제하는 규칙을 넣을 때는,
그 방식이 게임의 다른 축(생존·성장·수급)에서 무엇을 잃는지 함께 봐야 한다.**
피해량만 보면 둘 다 멀쩡해 보였다.

**② 속성 조합**

무기마다 속성이 하나씩 붙고, 서로 다른 속성을 함께 들면 조합이 열린다.
조합 규칙은 타이틀 화면에 **공개**돼 있다 — 외우는 게임이 아니라 설계하는 게임이 되도록.

| 조합 | 효과 |
| --- | --- |
| 화염 + 뇌전 → 폭발 연쇄 | 처치 시 폭발이 번진다 |
| 냉기 + 물리 → 빙결 처형 | 둔화된 적이 받는 물리 피해 +45% |
| 신성 + 피 → 흡혈 전환 | 가한 피해의 일부를 회복 (초당 상한 있음) |
| 화염 + 신성 → 정화의 불길 | 모든 공격이 화상을 남긴다 |
| 뇌전 + 냉기 → 감전 폭풍 | 둔화된 적이 죽으면 연쇄 번개 |
| 피 + 물리 → 학살 | 처치할수록 피해 누적 (최대 +35%) |

무기 슬롯은 6개인데 무기는 8종이라, **무엇을 포기할지**가 곧 빌드 설계가 된다.

**③ 메타 진행 (영혼의 제단)**

판이 끝나면 처치 수와 생존 시간만큼 영혼을 얻고, 타이틀의 제단에서 영구 강화를 산다.
`localStorage` 에 저장되므로 브라우저를 닫아도 남는다.

### 개발 중 발견한 설계 결함

봇 시뮬레이션과 프로파일링으로 찾은 것들이라 기록해 둔다.

**1. 무적 시간이 '포위'의 위협을 지워버린다**

피격 후 0.6초 무적을 두면, 적 1마리에 닿으나 300마리에 둘러싸이나 받는 피해가 같아진다.
이 장르의 핵심 위협이 통째로 사라지고, 그래서 봇이 무한히 카이팅하며 이길 수 있었다.

→ **접촉 피해를 닿아 있는 적의 수에 비례**시켰다 (1마리 기준 × 1.0 ~ 최대 × 3.6).
포위당하는 것 자체가 위험해지고, 위치 선정이 실력이 된다.

**2. 빌드 상한이 너무 높으면 위협이 통째로 사라진다**

봇에 계측을 붙여 "최저 HP"와 "피격 횟수"를 재보고 알았다.
난이도를 아무리 올려도 봇이 이기길래 수치가 문제인 줄 알았는데,
실제로는 **15분 동안 피격 0회**였다. 밸런스가 쉬운 게 아니라,
15분에 레벨 70이 나와서 무기·패시브가 전부 최대치가 되고,
그 화력에 아무것도 플레이어 근처까지 오지 못하고 녹아버린 것이었다.

→ 경험치 곡선을 세워 한 판의 상한을 낮췄다. 무기 슬롯이 6칸인데 무기가 8종이라는
설계도 같은 목적이다 — **다 가질 수 없어야 선택이 의미를 갖는다.**

관련해서 하나 더 찾았다. 봇 로그에 `피격 1회 · 최저 HP 0%` 가 찍혔는데,
**풀피에서 한 대 맞고 즉사**했다는 뜻이다. 포위 비례 피해 × 후반 피해 배수가 겹치면
가능한 값이었다. 대응할 기회 없이 죽는 건 어렵다고 느껴지는 게 아니라 억울하다고 느껴진다.

→ 한 번에 받는 피해를 **최대 체력의 45%로 제한**했다. 풀피에서는 항상 최소 두 대를 버틴다.
포위는 여전히 치명적이지만(1.2초 안에 두 대), 죽는 이유를 플레이어가 이해할 수 있다.

**3. 병목은 렌더가 아니라 update 였다**

적 340마리에서 프레임이 떨어져 렌더링부터 최적화했는데(shadowBlur 제거, 그림자·보석 배칭)
거의 나아지지 않았다. 구간별로 끄면서 측정해 보니 렌더는 전체의 일부였고,
진짜 범인은 `nearestEnemies` 였다 — 호출마다 수백 개의 객체를 할당하고 정렬하는데,
유도 발사체가 이걸 **매 프레임** 부르고 있었다.

→ 풀을 한 번 선형 순회하며 상위 k개만 삽입 정렬로 유지하도록 바꾸고(할당·정렬 0),
유도 재탐색을 초당 5회로 제한했다. **update 비용이 프레임당 0.53ms** 로 떨어졌다.

교훈: 최적화는 측정하고 시작한다. 추측으로 고친 렌더링은 2fps 벌었고, 측정으로 찾은 건 한 자릿수 배였다.

### 밸런스 튜닝 지점

한 곳에 모여 있으니 여기만 만지면 된다.

- `Game.difficulty()` — 시간에 따른 적 체력/속도/피해 배수
- `Game.targetCount()` — 동시 등장 수 상한
- `WEAPONS[*].dmg / cd / count` — 무기 레벨별 수치
- `player.xpNext` 공식 — 성장 속도

봇 시뮬레이션으로 4직업 × 3회 15분 완주를 돌려 곡선을 맞췄다.

**단, 봇은 난이도의 하한선일 뿐이다.** 이 봇은 적에게서 밀려나는 방향으로만 움직이는데,
그게 사람보다 카이팅을 잘한다. 그래서 봇이 완주한다고 사람도 쉽다는 뜻이 아니다.
반대로 봇이 죽는 지점(현재는 5분 보스 구간)은 사람에게도 확실히 어렵다는 신호다.

봇을 이기게 만들려고 수치를 계속 올리는 건 잘못된 방향이었다.
대신 **카이팅 자체를 못 하게 만드는 설계**를 넣는 쪽이 맞았다 —
포위 비례 피해, 그리고 7분 이후의 사냥개 무리(플레이어보다 빠르다).

최신 측정(4직업 × 3회, 피해 상한 적용 후):

| 직업 | 결과 | 최저 HP | 15분간 피격 |
| --- | --- | --- | --- |
| 성기사 | 3승 | 64~95% | 2~3회 |
| 전사 | 3승 | 55% | 1~5회 |
| 추적자 | 3승 | 55~100% | 0~2회 |
| 마법사 | 3승 | **100%** | **0회** |

**여기서 볼 것은 승패가 아니라 마지막 줄이다.** 마법사만 세 판 모두 한 대도 맞지 않았다.
사거리가 가장 길어서 완벽하게 카이팅하는 봇과 궁합이 지나치게 좋다는 뜻이고,
사람이 잡아도 "위험을 느낄 일이 없는" 직업이 될 소지가 크다.
사거리를 줄이거나, 마법사에게만 근접을 강제하는 압박(순간이동 적 등)이 필요할 수 있다.
**플레이테스트에서 가장 먼저 확인할 항목.**

**최종 밸런스는 사람이 직접 해봐야 한다.**

## 2. 그래픽 리소스를 어떻게 할 것인가

지금은 전부 코드로 그린 도형이다. 프로토타입으로는 최선이지만(반복이 빠르고 리소스 대기가 없다)
상품이 되려면 못 쓴다. 순서는 이렇다.

### 2-1. 아트 스타일을 먼저 정한다 — 이게 곧 비용이다

| 스타일 | 물량 | 외주 단가 | 이 장르 적합성 |
| --- | --- | --- | --- |
| **픽셀아트 32×32** | 낮음 (프레임 2~4장) | 낮음 | ★★★ 장르 표준, 몹 수백 마리가 겹쳐도 읽힌다 |
| 벡터/플랫 | 중간 | 중간 | ★★ 해상도 자유롭지만 톤이 안 맞기 쉽다 |
| 손그림 HD | 높음 | 높음 | ★ 몹 30종 만들다 끝난다 |
| 3D 탑다운 | 높음 | 매우 높음 | ✗ 몹 300마리 = 인스턴싱/LOD 필수, 1인 개발엔 비추천 |

→ **픽셀아트 32×32 권장.** 몹이 화면을 덮는 장르라 실루엣만 읽히면 되고, 물량을 감당할 수 있는 유일한 선택지다.

### 2-2. 실제로 필요한 물량 (정식 출시 기준 현실 산정)

- 적: 30~40종 × (걷기 4프레임 + 피격 1) ≈ 200장
- 보스: 5~8종 × 6~8프레임 ≈ 50장
- 플레이어: 직업 8종 × 2방향 × 4프레임 ≈ 64장
- 무기/스킬 이펙트: 25종 × 5~8프레임 ≈ 150장 ← **여기가 제일 많이 든다**
- UI 아이콘: 무기·패시브·유물 합쳐 100개 이상
- 배경 타일셋: 스테이지 5종
- 폰트, 프레임, 커서 등

이펙트가 캐릭터보다 비싸다는 걸 놓치는 경우가 많다. 이 장르는 이펙트가 곧 손맛이다.

### 2-3. 조달 경로 (단계별)

1. **프로토타입~내부 테스트**: CC0 에셋 팩 (Kenney, itch.io 무료 팩).
   재미 검증 단계에서 아트에 돈을 쓰면 안 된다.
2. **데모/얼리액세스**: 인상에 직결되는 것만 외주 — 플레이어 캐릭터, 시그니처 이펙트, UI 프레임, 로고.
   나머지는 유료 팩으로 채운다. 예산 대비 체감이 가장 크다.
3. **정식 출시**: 전량 커스텀으로 통일. 스타일이 섞이면 "에셋 조립 게임"으로 보이고 리뷰에서 바로 지적당한다.

외주는 픽셀아트 아티스트 기준 스프라이트 1세트(4프레임) 단위로 견적을 받는 게 관리하기 쉽다.

### 2-4. 라이선스 — 출시 전에 반드시 정리

- 팩마다 **상업 이용 / 재배포 / 크레딧 의무**를 확인하고 스프레드시트로 관리한다.
  (CC0 = 자유, CC-BY = 크레딧 필수, 일부 팩은 "게임에 포함은 되지만 에셋 자체 재판매 금지")
- 한글 폰트가 특히 함정이다. 상업 이용 가능하고 게임 임베딩이 허용된 것만 쓴다 (예: OFL 라이선스 폰트).
- **생성형 AI로 만든 에셋을 쓴다면 스팀 스토어 페이지에 공시 의무가 있다.**
  학습 데이터 출처 문제로 리뷰 리스크도 있으니, 쓸 거면 컨셉 시안까지만 쓰고 최종 에셋은 사람이 그리는 쪽을 권한다.

### 2-5. 교체 지점은 이미 만들어 뒀다

에셋이 없어도 **교체 가능한 구조**는 미리 넣을 수 있고, 넣어 뒀다 (`Sprites`).

```js
// 아트가 들어오는 날, 이 한 줄만 추가하면 도형 렌더링이 스프라이트로 바뀐다
Sprites.load("atlas.png", {
  bat:    { x: 0,   y: 0, w: 32, h: 32, n: 4, fps: 8 },
  zombie: { x: 128, y: 0, w: 32, h: 32, n: 4, fps: 6 },
  // ...
});
```

- `Sprites.draw(key, ...)` 는 프레임이 있으면 그리고 `true`, 없으면 `false` 를 돌려준다.
  `drawEnemy()` 는 `false` 일 때만 기존 도형 렌더링으로 폴백한다.
  → **적별로 하나씩 점진 교체**가 가능하다. 전부 준비될 때까지 기다릴 필요가 없다.
- 아틀라스 로딩에 실패해도 도형 렌더링으로 계속 돌아간다.
- `ENEMY_TYPES` 의 각 항목에 이미 `sprite: "bat"` 같은 키가 들어가 있다.
- 픽셀아트를 전제로 `imageSmoothingEnabled = false` 로 그린다.

무기 이펙트도 같은 방식으로 확장하면 된다 (현재는 각 무기의 `draw()` 가 분리돼 있다).

## 3. 차별화 — 아류작 홍수에서 살아남기

이 장르 클론이 실패하는 이유는 대부분 같다.
**"무기 6개 + 레벨업 3택"이라는 껍데기만 복사하고, 빌드가 서로 상호작용하지 않는다.**
30분 하면 볼 게 없다는 뜻이고, 리뷰에 "그냥 VS인데 더 못 만듦"이라고 적힌다.

성공한 후발주자들은 축을 하나씩 확실히 비틀었다.

| 게임 | 비튼 축 |
| --- | --- |
| Halls of Torment | 능동 조작(조준·스킬)과 디아블로식 장비/퀘스트 |
| Brotato | 라운드제 + 상점 → 빌드를 "설계"하게 만듦 |
| Deep Rock Galactic: Survivor | 지형 채굴이라는 별도 자원 루프 |
| 20 Minutes Till Dawn | 수동 조준 + 카드 시너지 |

### 이 게임에 추천하는 축 — 이미 말한 방향과 맞는다

"직업이 있고, 공격과 스킬의 개념이 서로 맞았으면 좋겠다"는 요구는 사실 **차별화 축 그 자체**다.
두 가지를 묶으면 한 줄 훅이 나온다.

**① 직업마다 다른 자원 루프 (조작 깊이)**

순수 오토배틀이 아니라, 직업마다 다른 방식으로 차오르는 자원과 그걸 쓰는 능동 스킬 1~2개를 준다.
"언제 쓰느냐"의 판단이 생기면서 실력 차이가 드러난다.

- 성기사 — **신앙**: 피격당할 때 충전 → 위기에 강해지는 역설. 방어적 플레이 보상
- 전사 — **분노**: 적을 처치할수록 충전 → 몰아쳐야 유지됨. 공격적 플레이 강제
- 추적자 — **집중**: 피격당하지 않은 시간에 비례 → 무피격 유지가 보상
- 마법사 — **마나**: 시간에 따라 충전, 스킬이 비쌈 → 자원 관리형

같은 맵을 4번 해도 플레이 리듬이 다르다. 이게 "직업이 있다"의 진짜 값이다.

**② 속성 조합 (빌드 깊이)**

VS의 "진화"는 정해진 짝 하나뿐이라 정답 암기 게임이 된다.
대신 무기에 **속성(화염/냉기/뇌전/신성/피)** 을 붙이고, 조합 규칙을 명시적으로 공개한다.

- 화염 + 뇌전 = 폭발 연쇄
- 냉기 + 물리 = 빙결 후 처형 피해 증폭
- 신성 + 피 = 흡혈 전환

조합 규칙이 공개돼 있으면 플레이어가 **설계**를 하게 되고,
조합 수가 곱으로 늘어나 콘텐츠 대비 플레이타임이 길어진다.
"공격과 스킬의 개념이 맞는다"는 요구도 여기서 자연히 충족된다 — 속성이 곧 공통 언어가 된다.

### 한 줄 훅 테스트

스팀 짧은 설명(최대 300자)에 들어갈 한 문장이 안 나오면 차별화가 안 된 것이다. 예:

> "직업마다 다른 자원으로 능동 스킬을 굴리고, 속성을 조합해 나만의 마법을 만드는 중세 판타지 서바이벌"

이 문장이 스크린샷 3장과 함께 위시리스트를 결정한다.

### 하지 말아야 할 차별화

- 무기 종류만 늘리기 (깊이가 아니라 양)
- 스토리/컷신 (이 장르 플레이어는 안 본다)
- 하드코어 난이도 (진입장벽만 올라감)

## 4. 스팀 출시

**맞다. 이 장르는 스팀이 사실상 유일한 주 시장이다.**
모바일은 광고형 아류로 포화됐고, 콘솔은 스팀에서 검증한 뒤 이식하는 순서가 맞다.

### 준비물

- Steamworks 파트너 등록: **수수료 $100** (해당 앱 매출 $1,000 넘으면 환급)
- 세금 정보(W-8BEN), 은행 계좌, 사업자 여부 결정
- 스토어 페이지 심사 → 빌드 심사, 각각 며칠 걸린다

### 일정 — 위시리스트가 전부다

출시 성적은 **출시일 위시리스트 수**로 거의 결정된다.

1. **출시 최소 3~6개월 전** 스토어 페이지 오픈 (게임이 미완성이어도 된다)
2. 트레일러 1개 + 스크린샷 5장 — 게임플레이 3초 안에 보여줄 것
3. **데모 필수.** 이 장르는 10분 해보면 살지 말지 결정된다. 데모 없이 출시하면 손해다
4. **Steam Next Fest는 게임당 한 번뿐**이다. 데모가 충분히 재밌어진 다음에 쓴다
5. 얼리액세스가 잘 맞는 장르다 (콘텐츠 추가형). 단, EA 시작 시점에도 "이대로도 재밌다" 수준은 돼야 한다

### 체크리스트

- [ ] 한국어 / 영어 / 중국어 간체 로컬라이즈 (이 장르는 중화권 매출 비중이 크다)
- [ ] **스팀 덱 호환성 인증** — 이 장르는 덱 수요가 특히 크다. 컨트롤러 입력과 UI 크기를 초기부터 고려
- [ ] 실적(Achievements) — 리텐션에 실제로 효과가 있다
- [ ] 클라우드 세이브
- [ ] 생성형 AI 사용 시 공시
- [ ] 스팀 리뷰 초반 대응 계획 (첫 2주 리뷰 점수가 알고리즘 노출을 좌우한다)

### 엔진 선택

웹/Canvas 프로토타입은 **재미 검증용**으로는 최적이지만, 상용 출시는 옮기는 편이 낫다.

- **Godot 4** 권장 — 무료, 2D 강력, 스팀 통합(GodotSteam) 성숙, 픽셀아트 워크플로 좋음
- Unity도 가능하지만 이 규모에선 오버스펙이고 라이선스 정책 리스크가 있다
- 웹 그대로 Electron 래핑도 되지만, 스팀 실적/클라우드/덱 대응에서 손해를 본다

**단, 옮기는 건 재미가 검증된 다음이다.** 지금 프로토타입으로 "20분을 계속 하게 되는가"를 먼저 확인할 것.
