# 그래픽 리소스 규격 — 「스테인드글라스 실루엣」

이 문서 하나로 그림을 발주하거나 직접 그려 넣을 수 있게 쓴 것이다.
**코드는 이미 준비돼 있다.** 규격대로 시트를 만들어 물리면 게임 코드는 한 줄도 안 바뀐다.

레퍼런스 아틀라스가 `art/reference-atlas.png` 에 들어 있다. 최종 아트가 아니라
**자리 표시자 겸 기준자**다 — 같은 칸에 같은 크기로 덮어 그리면 그대로 교체된다.

---

## 1. 왜 이 스타일인가

화면에 적이 **최대 340마리**까지 뜬다. 디테일이 많은 도트나 반실사는 그 밀도에서
뭉개진다. 실제로 이 프로젝트에서 반복해서 부딪힌 제약은 항상 "밀도"였다 —
몬스터 이름표도 겹침 때문에 표시 개수를 26개로 제한해야 했다.

그래서 **실루엣과 색 대비만 남기는** 스타일을 택한다. 성당 스테인드글라스가
정확히 그 구조다: 굵은 납선(윤곽) + 투과광(발광색). 템플러 컨셉과도 맞고,
신성·화염·냉기·뇌전 속성이 그대로 유리색이 된다.

## 2. 스타일 규칙 4개

| | 규칙 |
| --- | --- |
| **윤곽** | 모든 유닛에 굵은 검은 윤곽(`#0a0a12`). 프레임 크기의 **10~16%** 두께. 배경과 무조건 분리된다 |
| **색** | 유닛당 **주색 1 + 발광색 1**. 세 번째 색은 쓰지 않는다 |
| **발광** | 위험한 것만 빛난다 — 보스, 정예, 예고 범위, 수정 기둥, 화톳불 |
| **배경** | 채도를 유닛의 절반 이하로. 지형은 어둡게 깔리고 적만 뜬다 |

주색은 게임 데이터의 `ENEMY_TYPES[*].color` 를 그대로 쓴다. 색을 새로 정하지 말 것 —
미니맵·피격 파티클·체력바가 전부 같은 값을 참조한다.

## 3. 프레임 크기 — 이 계산이 규격의 핵심이다

호출부는 `Sprites.draw(key, sx, sy, 적반지름 / 14, ...)` 로 그린다. 즉

```
화면에 그려지는 폭 = 프레임 폭 w × (적 반지름 r / 14) × (프레임의 s, 기본 1)
```

히트박스 지름은 `2r` 이므로, **그림이 히트박스와 정확히 겹치려면 `w × s = 28`** 이어야 한다.

| 프레임 | `s` | 결과 |
| --- | --- | --- |
| 28 × 28 | 1 | 히트박스와 정확히 일치 |
| **32 × 32** | 1 | 1.14배 — 살짝 넘치게 그려져 보기 좋다. **일반 몬스터 기본값** |
| **64 × 64** | **0.438** | 화면 크기는 32px 짜리와 같고 **픽셀 밀도만 2배**. **보스 기본값** |

보스는 반지름이 42~50 이라 32px 프레임을 3배 이상 확대하게 되어 뭉개진다.
그래서 큰 프레임을 쓰고 `s` 로 되돌린다.

`ox` / `oy` 로 기준점을 옮길 수 있다(기둥처럼 위로 긴 그림을 발밑에 맞출 때).

## 4. 시트 배치

```
가로 = 프레임 폭 × 프레임 수      (애니메이션은 가로로 나열)
세로 = 종류마다 한 줄씩 아래로
```

- 애니메이션 **4프레임**, 기본 **8fps**. 빠른 것(박쥐·사냥개)만 10fps
- 여백·패딩 없음. 프레임은 정확히 맞닿는다
- 배경 투명 PNG. 보간이 꺼져 있으므로(`imageSmoothingEnabled = false`) 반투명 가장자리는 지저분해진다 — **안티에일리어싱 없이** 그릴 것
- 좌우 반전은 코드가 처리한다(`flip`). **오른쪽을 보는 그림만** 그리면 된다

## 5. 그려야 하는 것 — 17종, 그러나 실루엣은 6종

`ENEMY_TYPES[*].shape` 가 이미 6종으로 묶여 있다. **17장을 새로 그리지 말고
실루엣 6종을 그린 뒤 색만 바꾸는 것**을 권한다.

| 실루엣 | 쓰는 몬스터 |
| --- | --- |
| `bat` | 박쥐 |
| `blob` | 슬라임 · 분열체 · 폭발체 |
| `ghost` | 유령 · 사신 · 주술사 |
| `humanoid` | 좀비 · 괴수 · 사수 · 돌진자 · 방패병 |
| `hound` | 사냥개 |
| `boss` | 제단의 파수꾼 · 역병 군주 · 강철 처형자 · 심연의 왕 |

**등급(정예·희귀)은 추가 그림이 필요 없다.** 코드가 테두리와 크기(×1.24 / ×1.5)로
구분하고 이름표를 붙인다.

## 6. 물리는 법

```js
Sprites.load("atlas.png", {
  bat:   { x: 0, y:   0, w: 32, h: 32, n: 4, fps: 10 },
  slime: { x: 0, y:  32, w: 32, h: 32, n: 4, fps: 8  },
  // ...
  boss1: { x: 0, y: 480, w: 64, h: 64, n: 4, fps: 8, s: 0.438 },
});
```

`art/atlas-frames.json` 이 레퍼런스 아틀라스에 맞는 프레임 정의다. 그대로 붙여 쓰면 된다.

**로드에 실패해도 게임은 그대로 돈다** — `Sprites.draw` 가 `false` 를 돌려주면
호출부가 도형 렌더링으로 폴백한다. 그래서 아트를 한 종류씩 넣어도 되고,
넣다 만 상태로 배포해도 깨지지 않는다.

> 현재 배포본은 **도형 렌더링**을 쓴다. 아티팩트는 외부 파일을 실을 수 없어서,
> 아틀라스를 켜면 아티팩트와 GitHub Pages 가 서로 달라 보이기 때문이다.
> 전면 교체할 때 `Sprites.load` 한 줄을 켜면 된다(PNG 를 data URI 로 넣으면 아티팩트에서도 된다).

## 7. 조달 순서 — 비용 대비 효과 순

1. **실루엣 6종**을 먼저 확보한다. itch.io 의 CC0 실루엣 팩으로 시작해도 된다
2. 반응이 오면 **보스 3종 + 직업 4종**만 전용 아트로 교체한다. 화면에서 가장 오래 보이고
   가장 크게 보이는 것들이다
3. 지형 12종은 **가장 나중**이다. 지금 도형으로도 종류가 구분되고, 크기 편차가
   이미 이정표 역할을 한다

## 8. 레퍼런스 아틀라스 다시 만들기

```sh
node art/make-atlas.js     # art/reference-atlas.png 와 atlas-frames.json 을 다시 뽑는다
```

몬스터를 추가하면 `art/atlas-spec.json` 에 한 줄만 넣으면 된다.
색과 실루엣은 게임 데이터에서 그대로 가져오므로 어긋날 일이 없다.

## 9. 주인공 — 직업 4종 × 동작 4종

몬스터는 단색 실루엣이지만 주인공은 그럴 수 없다. 화면 가운데에서 가장 오래 보이는 것이
한 덩어리 색이면 무엇을 들고 있는지, 지금 무엇을 하고 있는지 읽히지 않는다.
그래서 주인공만 팔레트를 늘렸다.

| 글자 | 쓰임 |
|---|---|
| `A` / `a` | 직업색과 그 그늘 (망토·문양·로브) |
| `S` / `s` | 살 · 살 그늘 |
| `M` / `m` | 강철 · 강철 그늘 |
| `L` / `l` | 가죽 · 가죽 그늘 |
| `W` | 날 끝 광택 · 영창의 빛 |

동작 4종과 각 지속시간(`ACT_DUR` · `CAST_DUR` 은 프레임 4장 ÷ fps 라서 정확히 한 바퀴만 돈다):

| 동작 | fps | 언제 |
|---|---|---|
| `idle` | 6 | 멈춰 있을 때 |
| `walk` | 10 | `player.moving` |
| `attack` | 14 | 무기가 나갈 때(`player.actT`) · 돌진 중 |
| `cast` | 12 | 직업 스킬을 쓸 때(`player.castT`) |

키는 `hero_<직업키>_<동작>` 이다. 오른쪽을 보게만 그리고 왼쪽은 `player.flip` 으로 뒤집는다.
`player.faceX` 는 조준에도 쓰이므로 반전 판정에 쓰지 않는다 — 세로로만 움직이면 0 이 된다.

읽히게 만들려고 실패한 것들:

* 망토를 몸 폭만큼 넓히면 **치마**가 된다 → 왼쪽 뒤로만, 다리는 덮지 않는다
* 무기를 1~2px 로 얇게 그리면 게임 크기에서 **사라진다** → 굵게, 끝에 흰 광택
* 광택을 날 전체에 그으면 날이 **두 배로 두꺼워** 보인다 → 끝 2px 만
* 영창에 두 팔을 올리면 **살색 덩어리**가 된다 → 한 팔만 들고 빛은 무기 앞 한 점에 모은다
* 도끼·지팡이를 수평으로 들면 **걸레·빗자루**다 → 직업별 평상시 각도를 따로 둔다
* `outline()` 은 겉만 잡는다. 허리·다리 사이·투구 틈은 **직접 검은 선**을 그어야 형태가 갈린다

## 10. 이펙트 — 4종 × 속성 6종

타격·폭발·베기·시전이 전부 원과 `shadowBlur` 뿌연 광원이었다. 몬스터와 주인공을
픽셀로 바꾸고 나니 이펙트만 재질이 달라 겉돌았다. 같은 방식으로 픽셀로 찍는다.

| 종류 | 크기 | fps | 언제 |
|---|---|---|---|
| `fx_hit_*` | 32 | 22 | 적이 맞을 때 |
| `fx_boom_*` | 48 | 13 | 처치 · 파동(폭발) · 낙뢰 |
| `fx_slash_*` | 48 | 17 | 근접 베기 (호출부가 각도로 회전) |
| `fx_cast_*` | 32 | 20 | 무기가 나갈 때 |

키는 `fx_<종류>_<속성>` 이고 속성은 물리·화염·냉기·뇌전·신성·피 6종이다.
없는 속성은 `fxKey()` 가 물리로 떨어뜨린다.

이펙트는 몬스터·주인공과 규칙이 다르다.

* **검은 윤곽을 두르지 않는다.** 빛이기 때문이다 — 각 실루엣이 `outline()` 을 부르지 않는다
* **`s`(축소 배수)를 넣지 않는다.** 프레임 크기가 종류마다 달라, `spawnFx` 가
  화면 픽셀 크기를 직접 받고 `px / fr.w` 로 배수를 계산한다. 스펙의 `fx: true` 가 그 표시다
* **색이 `ELEMENTS` 와 다르다.** 가산 합성으로 그리므로 물리(`#d8d8e4`)·신성(`#ffd9a0`) 을
  그대로 쓰면 어두운 배경 위에서 흰 덩어리가 된다. 이펙트에만 채도를 올린 값을 쓴다
  (`#93a6c4` · `#ffc266`). UI·미니맵 색은 건드리지 않는다

혼잡할 때 스스로 줄어든다:

* 적 하나당 `e.flash` 가 남아 있으면 타격 이펙트를 건너뛴다 — 0.12초에 한 번
* 살아 있는 이펙트가 70개를 넘으면 새 타격 이펙트를 포기한다(`fxLive`).
  200마리를 한꺼번에 때리면 불꽃이 서로를 밀어내 죄다 중간에 잘리고 뿌연 덩어리가 된다.
  그럴 바엔 안 그리는 편이 낫다. 치명타만 예외로 항상 그린다
* 배열을 훑어 세면 초당 천 번씩 도는 셈이라 `fxLive` 를 증감으로 관리한다

그리기는 **가산 합성을 루프 바깥에서 한 번만 켠다**. 이펙트마다 `globalCompositeOperation`
을 갈아 끼웠더니 그 전환만으로 프레임이 눈에 띄게 느려졌다.

## 11. 큰 이펙트 — 스프라이트로는 못 그린다

지난 절에서 베기를 `fx_slash` 스프라이트로 그렸다. 그게 틀렸다.

`Sprites.draw` 는 프레임을 확대해서 그린다. 베기의 사거리는 무기마다 다르다 —
쇠사슬 플레일 92, 8레벨 268, 심판의 빛 **520**. 48px 한 장을 520 에 맞추면
**25배 확대**다. 실제로 그렇게 배포했고 화면 1/3을 덮는 계단 모양 덩어리가 나왔다.

기준은 이렇다. **주변 스프라이트가 1:1 로 그려지는데 혼자 몇 배로 확대되면
같은 화면의 픽셀 크기가 어긋난다.** 3배가 한계다.

그래서 큰 이펙트는 화면 픽셀 격자(`PIX = 3`)에 맞춰 직접 찍는다.
길이가 92든 520이든 눈에 보이는 픽셀 크기가 같다.

| 함수 | 쓰는 곳 |
|---|---|
| `pxArc` | 베기 (사거리 300 이하) — 휘두르는 초승달 |
| `pxLance` | 베기 (사거리 300 초과) — 앞으로 내지르는 빛의 창 |
| `pxRing` | 파동 — 퍼져 나가는 고리 |
| (인라인) | 낙뢰 — 꺾인 점 사이를 격자 칸으로 |

`spawnSlash` 에 종류를 따로 두지 않고 **사거리로 갈린다**. 300 을 넘는 베기는
전부 '앞으로 길게 뻗는' 스킬이고, 그걸 부채꼴로 그리면 화면을 덮기 때문이다.

### 두 번 크게 틀렸다

**① 순백을 심지로 썼다.** 이펙트는 가산 합성으로 그린다. `[흰색, 중간, 속성색]`
으로 깔았더니 화염·냉기·신성 파동이 **전부 회색 고리**로 나왔다. 흰색이 겹치는
순간 색이 날아간다. 게다가 물리(`#d8d8e4`)·신성(`#ffd9a0`)은 이미 밝아서
더 밝힐 데도 없다. 그래서 `pxPal` 이 밝기를 보고 갈린다 —
어두운 색은 밝혀서 겉을 만들고, 밝은 색은 **원색을 몸통으로 두고 아래로 깐다**.

**② 칸마다 `fillStyle` 을 갈고 `fillRect` 를 불렀다.** 최악의 프레임에서
**5.8 → 30ms**. 칠할 색은 세 가지뿐이므로 좌표만 쌓아 두었다가 색당 한 번씩
`path` 로 칠한다(`pxPush` / `pxFlush`). 30 → 7.9ms 로 돌아왔다.

계측(적 200 + 긴 베기 3 + 파동 2 + 낙뢰 3 이 매 프레임 살아 있는 인위적 최악):
이전 4.5~7.8ms · 현재 7.3~8.7ms. 일반 전투(적 200, 이펙트 폭주 없음)는
2.2~2.8 vs 2.6~3.4ms 로 겹친다.

## 12. 발사체 — 스프라이트를 쓸 수 없는 이유

발사체는 반지름 5~45 라 스프라이트를 써도 3배 이내다. 규격상으로는 가능하다.
그런데 못 쓴다 — **무기마다 색이 제각각이기 때문이다.**
`spawnProjectile` 이 받는 `color` 는 속성이 아니라 무기별 값이라, 아틀라스에
색깔 수만큼 줄을 넣을 수는 없다. 그래서 여기도 격자로 찍는다.

`pxDisc` 는 **원을 그린 뒤 테두리에 칸을 덧찍지 않는다.** 가로줄로 직접 찍는다 —
안쪽까지 전부 격자에 맞아 진짜 픽셀 원이 되고, 테두리를 따로 도는 비용도 없다.
(테두리를 덧찍는 방식으로 먼저 만들었다가 탄 200발에서 7.6~9.9 → 11.4~11.8ms 로
느려졌다. 가로줄 방식으로 바꾸니 8.2~10.6ms 로 겹친다.)

| 종류 | 그리는 법 |
|---|---|
| 구체 · 불꽃 | `pxDisc` — 겉/속 두 겹. 불꽃은 날아가며 사그라든다 |
| 단검 | 꼭짓점을 직접 돌려 채우고 `pxEdge` 로 테두리 |
| 적 탄 | 붉은 `pxDisc` 위에 제 색 `pxDisc` — 아군 탄과 절대 헷갈리면 안 된다 |

단검만 회전이 필요한데, **회전된 좌표계에서 칸을 찍으면 안 된다.**
격자는 화면 좌표 기준이라 변환 아래에서는 어긋나고 안티에일리어싱이 되돌아온다.
꼭짓점 세 개를 직접 돌려 화면 좌표로 만든 다음 찍는다.

## 13. 바닥 장판

장판은 '점'이 아니라 '면'이다. 발사체처럼 꽉 찬 원으로 그리면 웅덩이가 아니라
색칠한 바닥이 된다. 그래서 셋으로 나눈다.

* **속** — 가로줄로 찍은 옅은 원. 발밑이 어디까지 위험한지 면으로 보인다
* **테두리** — 격자 칸을 **한 칸씩 띄운 점선**. 촘촘히 두르면 장판 하나당 200칸이라
  오래 남는 효과치고 비싸고(장판 6개에 +1.6ms), 점선이 오히려 '여기까지가 구역'으로
  더 잘 읽힌다. 띄우니 +0.6ms 로 내려갔다
* **방울** — 저마다 다른 주기로 떴다 사라지는 칸 16개. 평평한 원에 생기를 준다.
  위치는 `hash2` 로 뽑아 프레임마다 흔들리지 않는다

### 정리 — 무엇을 무엇으로 그리는가

| 크기 | 방법 | 예 |
|---|---|---|
| 고정 크기, 색이 유한 | **스프라이트** (1:1~3배) | 몬스터 · 주인공 · 타격/폭발/시전 |
| 크기가 변하거나 색이 자유 | **격자 렌더** | 베기 · 파동 · 낙뢰 · 발사체 · 장판 · 성역 |

기준은 하나다. **주변 스프라이트가 1:1 인데 혼자 몇 배로 확대되면 어긋난다.**

## 14. 대형 구조물

지형지물(상자·제단·비석)은 한 번 만지고 끝나는 '점'이다.
구조물은 '장소'다 — 켜 두고 그 자리를 지켜야 값을 한다.
크기도 다르다. 반지름 110~180 으로 기존 지형의 두 배 이상이다(폐허가 40~96).

크기가 종류마다 다르고 켜짐/꺼짐으로 색이 바뀌므로 **격자 렌더**다(12·13절의 규칙).

멀리서 실루엣이 구분되어야 갈지 말지를 정할 수 있다. 그래서 윗부분의 형태를 다르게 한다 —
첨탑은 뾰족하게, 샘은 낮고 둥글게, 성채는 톱니, 대장간은 굴뚝.
꺼져 있을 때도 종류색을 조금 섞는다. 전부 같은 회색이면 멀리서 무엇인지 모른다.

큰 면이 비어 있으면 건물이 아니라 판자로 보인다. 그래서 어두운 구멍을 판다 —
첨탑의 띠, 샘의 기둥 사이 그늘, 성채의 화살 구멍과 성문, 대장간의 입구.

## 15. 남은 곳을 전부 — 바닥과 배경

「픽셀이 도입되지 않은 곳이 없게」 전부 옮겼다.

### 바닥은 이제 아틀라스 타일이다

예전에는 체크무늬 사각형 + 머리카락 굵기 격자선이라, 주변이 전부 픽셀인데
바닥만 '비어 있는 판'으로 보였다. 64px 타일 4변종 + 장식 4종(금·자갈·풀·뼈)을
아틀라스에 넣고 좌표 해시로 고른다.

두 번 고쳤다.

* **알갱이 대비를 세웠더니 TV 노이즈가 됐다.** 바닥이 그 위의 몬스터·이펙트와
  싸운다. 두 단계로 줄이고 장식도 전부 어둡게 낮췄다(흰 뼛조각이 아이템처럼 보였다).
* **매 프레임 타일로 화면을 채우니 drawImage 가 275번이었다**(+1.8ms).
  화면보다 한 타일 큰 캔버스에 미리 그려 두고 카메라가 타일 경계를 넘을 때만
  다시 그린다 — 보통 프레임은 blit 한 번이다.

### 지형 12종

`arc` · `stroke` · 다각형 `fill` 을 전부 걷어내고 주사선 방식으로 옮겼다.
색은 세 겹이다 — 겉(어두움) · 몸통 · 윗면(밝음). 위에서 빛이 온다.

실루엣도 손봤다. 덩어리로 그리면 안 되는 것들이 있었다 —
**석벽**은 공이 되고 **폐허**는 웅덩이가 됐다. 벽은 네모나야 벽이고,
폐허는 높이가 들쭉날쭉한 '무너진 벽'이라야 폐허다.
**거대 유해**는 갈비를 점으로 띄엄띄엄 찍어 부스러기로 보였다 — 촘촘히 이었다.

`pxBlob` 도 다시 짰다. 처음엔 '높이마다 폭'으로 계산했는데 `asin` 이 반원만
훑어서 좌우가 늘 대칭인 납작한 타원이 나왔다 — 바위가 아니라 비눗방울이었다.
지금은 꼭짓점을 흔든 다각형을 주사선으로 채운다.

### 그 밖에

그림자 · 보석 · 획득물 · 파티클 · 보스 예고 · 지형지물 셋 · 적 화상 광원.
획득물의 **이모지도 걷어냈다** — 폰트라 픽셀이 아니다. 고기 · 징표 · 약병 · 자석을
도형으로 직접 찍는다.

## 16. 로비 — 시작 화면 · 직업 선택 · 제단

세계는 전부 픽셀로 옮겼는데 로비만 남의 게임처럼 보였다. 두 가지가 원인이었다.

### 이모지

메뉴의 아이콘이 전부 이모지였다. 이모지는 **OS 폰트**라 기기마다 다른 그림이
뜨고, 무엇보다 안티에일리어싱된 벡터라 픽셀과 재질이 어긋난다.
`MENU_ICONS` 에 7×7 비트맵을 문자열로 적어 두고 `drawMenuIcon` 으로 찍는다.
`'.'` 은 빈칸, `2 · 1 · 0` 은 `pxPal` 의 밝은 곳 · 몸통 · 바탕이라
색 하나만 넘기면 3톤이 알아서 나온다.

넣은 것: 구슬 · 문장 · 검 · 마름모(속성) · 별(스킬) · 보석(전리품),
그리고 제단의 여섯 강화(강건함 · 예리함 · 민첩 · 탐욕 · 신념 · 부활).

**5×5 로 줄여 보기도 했는데 실패했다.** 그 크기에서는 검도 별도 마름모도
전부 `+` 로 뭉개져 서로 구분이 안 된다. 판은 7×7 로 두고, 글자 옆에 들어가는
자리는 칸을 2px 로 줄여 쓴다. 세계의 `PIX`(3) 보다 잘아지지만 글자 옆이라
그쪽이 훨씬 잘 읽힌다 — 격자 순수성보다 읽히는 쪽을 택했다.

### 정지 화면

세 화면 모두 불투명하게 덮고 있었다. 지금은 뒤에서 **어트랙트 데모**가
실제 시뮬레이션을 굴리고, 메뉴는 `menuScrim(a)` 로 덮어 가리기만 한다
(시작 .52 · 직업 선택 .68 · 제단 .70). 눌러 주는 띠와 불티도 여기 모아 둬
세 화면이 같은 재질로 보인다.

### 어트랙트 데모가 진짜를 오염시키지 않게

메뉴 뒤에서 진짜 `update()` 를 굴리는 이상, 데모가 남기는 흔적이 기록과
섞이면 안 된다. 조용히 망가지는 종류라 눈으로는 못 잡는다 — `tests/attract.js`
가 최고 기록 · 영혼 · 소리 · 상태 · 흔들림 · 음악 모드를 전부 지킨다.

소리는 `Sfx.muted()` 한 곳에서 막는다. 처음엔 `play()` 안에서만 막았는데,
**레벨업 · 사망 · 각성 팡파레는 `setTimeout` 으로 미룬 소리**라 시뮬레이션이
끝난 뒤에 울린다 — 메뉴에서 갑자기 레벨업 소리가 나는 것이다.
지금은 예약하는 쪽(`Sfx.arp`)에서도 본다.

테스트도 같이 고쳤다. `Sfx.play` 를 감싸 호출을 세면 **막힌 호출까지 세어**
멀쩡한 코드가 실패한다. 오디오 노드가 실제로 만들어졌는지를 세야
`play()` 를 거치지 않는 경로가 생겨도 걸린다.

## 17. 직업 카드 — 표를 걷어내고 무기를 돌린다

카드는 수치 표였다. 자세 · 무기 · 속성 · 자원 · 스킬 · 전리품 여섯 줄.
고르는 사람이 알고 싶은 건 그 표가 아니라 둘이다 —
**무엇을 들고 어떻게 싸우는가**, 그리고 **다른 직업과 견줘 어디가 세고 어디가 약한가**.

### 무기 무대

카드 안에 236×104 짜리 작은 무대를 놓고 시작 무기를 실제로 돌린다.
바닥은 `Sprites.drawTile("floor", …)` — 게임의 그 타일이다. 적도 게임의 스프라이트,
타격 이펙트도 `fxKey("hit", element)` 로 게임이 쓰는 그 프레임이다.
**여기서만 따로 그리면 미리보기가 아니라 거짓말이 된다.**

무기도 게임의 픽셀 함수를 그대로 부른다.

| 직업 | 무기 | 그리는 법 |
|---|---|---|
| 성기사 | 성역 | `pxRing` — 상시 결계가 주기마다 밝아지고, 그때 안에 든 적이 탄다 |
| 전사 | 쇠사슬 플레일 | `pxArc` — 부채꼴 참격. 맞는 판정도 사거리+각도로 게임과 같다 |
| 추적자 | 투척 단검 | 꼭짓점을 직접 돌린 사각형 + `pxEdge` — 관통하므로 첫 적을 지나 계속 난다 |
| 마법사 | 마법 화살 | `pxDisc` — 유도탄이라 곧게 가지 않고 옆으로 부풀었다 붙는다 |

주인공 초상은 뺐다. 무대 안에서 실제로 싸우므로 따로 세워 둘 이유가 없다.
카드마다 주기 위상을 어긋나게 해 네 장이 한꺼번에 번쩍이지 않게 했다.

**적을 작게 잡았다가 한 번 고쳤다.** 반지름 10~13 으로 두니 좀비가 사람이 아니라
덤불로 보였다. 15/13/12 로 키우니 실루엣이 산다.
성역은 결계라 적이 둘러싸야 하는데, 고리 반지름 58 은 무대 높이(104)를 넘어
위아래가 잘렸다 — 46 으로 줄이고 적을 고리 위에 앉혔다.

### 견줌 막대

생존 · 공격 · 기동 · 범위 · 전리품 다섯 축. 값은 `mods` 에서 뽑는다
(생존 = 체력 ÷ 방어 × 재생, 공격 = 피해 ÷ 쿨다운 × 치명).

**0 부터 그리면 안 된다.** 공격이 1.0~1.2 라 네 막대가 똑같아 보이고,
그러면 고르는 데 아무 도움이 안 된다. 네 직업의 최소~최대를 막대 폭에 펼친다.
바닥은 .18 로 띄운다 — 가장 낮은 것이 빈 칸이면 '없다'로 읽힌다.
절대값이 아니므로 카드 아래에 그렇게 적어 둔다.

### 조용히 죽는 것을 막는 테스트

무대는 조용히 죽는다. 위상 계산이 어긋나 이펙트 구간을 영영 못 만나거나
스프라이트 키가 바뀌어 적이 안 나와도, 화면은 멀쩡한 바닥 타일을 보여준다.
눈으로는 '좀 심심하네' 정도로만 보이고 아무도 버그라고 부르지 않는다.

`tests/class-cards.js` 가 한 주기를 240 등분해 훑으며,
직업마다 제 무기 함수가 불렸는지 · 타격 이펙트가 떴는지 · 적과 주인공이 그려졌는지 ·
캔버스 상태(알파 · 합성 모드)를 흘리지 않는지, 그리고 막대가 축마다 실제로 갈리는지 본다.

## 18. 제단과 재시작

### 제단에 제단이 없었다

「영혼의 제단」이라면서 화면에 제단이 없었다. 강화 카드 여섯 장이 허공에 떠 있고
그 아래는 빈 판이었다. 돌 받침 세 계단 · 홈을 판 기둥 · 대접, 그 위에 뜬 영혼 구슬을
격자로 찍는다. 모은 영혼도 별도의 숫자 줄이 아니라 이 제단이 들고 있게 했다 —
그래야 장식이 아니라 물건이 된다.

돌색은 **`pxPal` 에 맡기지 않는다.** 자주색 계열은 밝기 판정(`lum > .7`)에 걸려
세 톤이 전부 밝은 쪽으로 몰리고, 제단이 돌이 아니라 젖은 비누처럼 보였다.
`["#7a7392", "#4a4460", "#2b2540"]` 로 직접 잡았다 — 윗면 · 앞면 · 그늘.

부스러기는 대접에서 구슬까지만 띄웠더니 거리가 24px 뿐이라 아무것도 안 보였다.
기둥 전체를 쓰고, 오를수록 가운데로 모이게 해 구슬이 빨아들이는 것으로 읽히게 했다.
구슬도 한 번 올렸다 — 후광(반지름 40)이 대접을 덮고 있었다.

레벨 눈금의 `roundRect` 도 `pxR` 로 바꿨다. 여기만 둥근 모서리를 쓰면 재질이 어긋난다.

### 길이 끊겨 있던 곳

화면은 멀쩡한데 길이 끊긴 버그는 눈으로 안 잡힌다. 둘 있었다.

**어트랙트 데모가 전역 `selectedClass` 를 덮어썼다.** 타이틀에서 성기사를 골라 놓아도
데모가 새 판을 깔 때마다 고른 직업이 제멋대로 바뀌었다 — 카드 강조도 저 혼자 옮겨 다녔다.
`Game.reset(clsIdx)` 로 직업을 인자로 받게 하고, 데모는 제 직업을 따로 들고 다닌다.
「R 로 같은 직업 즉시 재시작」은 이걸 고치기 전에는 말이 안 되는 기능이었다.

**판이 끝난 뒤 갈 곳이 '다시 시작' 하나뿐이었다.** 죽어서 영혼이 들어왔는데 제단으로
갈 길이 없어 새로고침 말고는 방법이 없었다. 끝 화면에 갈래를 냈다 —
`SPACE`·`R` 같은 직업으로 즉시 · `ESC` 직업 다시 고르기 · `TAB` 영혼의 제단.
제단에 들어오는 네 길이 전부 `introFrom` 을 남기게 해서 `ESC` 가 제자리로 돌아간다
(전에는 세 곳이 안 남겨 이전 값이 그대로 쓰였다).

일시정지에도 `R` 을 넣되 **두 번 눌러야** 판을 버린다. 한 번에 날아가면 안 된다.

### 테스트

`tests/menu-flow.js` — 데모가 내 선택을 건드리지 않는지(그러면서 데모 자신은 여러
직업을 도는지) · 끝 화면의 세 갈래 · R 재시작이 같은 직업인지 · 포기가 두 번인지 ·
제단 구입이 키와 클릭에서 같은 길을 타는지 · 제단에서 들어온 곳으로 돌아가는지.

고치기 전 코드로 되돌려 돌려 봐서 실제로 잡히는 것을 확인했다 —
4개 항목이 실패하고 `내 선택 2/1` 로 직업이 밀려 있었다.

## 19. 영혼 경제 — 재고, 그리고 보이게 만들기

### 한 판이면 제단을 통째로 샀다

봇으로 판을 끝까지 굴려 재 봤다. 옛 정산식은 이랬다.

```
영혼 = 처치 ÷ 8  +  시간 ÷ 10  +  (클리어면 150)
```

문제는 **이 게임의 처치 수가 시간에 대해 폭발한다**는 것이다. 성기사 봇이 7분에
75,098마리, 8분에 94,669마리를 잡았다. 처치를 그대로 8로 나누니 한 판에
**9,429영혼**이 들어왔다. 제단 전체가 6,240이었다 — 잘한 판 하나로 전부 사고도 남는다.

화면에는 아무 이상이 없다. 숫자로만 잡힌다.

### 고친 식

```
영혼 = 시간 ÷ 6  +  60 × √(처치 ÷ 1000)  +  (클리어면 200)
```

처치는 제곱근으로 눌러 담는다 — 1,000마리 60 · 10,000마리 190 · 75,000마리 520.
잘한 판이 더 주긴 하되 **배수로 벌어지지는 않는다.** 주 수입은 '얼마나 버텼는가'로
옮겼다. 15분이라는 상한이 있어 폭발할 수 없는 값이다.

값도 다시 잡았다(전부 11,570). 계측된 판별 지급액과 제단 전체 대비 비율:

| 판 | 영혼 | 제단 대비 |
|---|---|---|
| 25초에 죽음 | 9 | 0.1% |
| 1분 35초 · 320마리 | 48 | 0.4% |
| 5분 10초 · 19,000마리 | 312 | 2.7% |
| 8분 05초 · 94,669마리 | 663 | 5.7% |
| 15분 클리어 · 200,000마리 | 1,198 | 10.4% |

첫 칸(90)은 첫 판이나 두 번째 판에 닿고, 전부 채우려면 서른다섯 판 안팎이 든다.

### 보이게 만들기

숫자를 고쳤으면 그 숫자가 읽혀야 한다.

**끝 화면** — 합계만 던지면 다음 판에 무엇을 더 해야 많이 버는지 알 수가 없다.
`버팀 8:05 → +80 · 처치 94,669 → +583` 로 내역을 편다. 버틴 시간이 주 수입이라는
설계가 여기서 읽힌다.

**제단 카드** — 「최대 체력 +8%」만 적어 두면 지금 내가 몇 %인지, 하나 더 사면
몇 %가 되는지 머리로 곱해야 한다. `최대 체력 +16% → +24%` 로 지금 값과 다음 값을
나란히 놓는다. `desc` 에 같은 숫자를 또 적어 두면 한쪽만 고칠 때 어긋나므로,
`per · step · unit` 에서 글을 만든다.

카드 아래에는 **모으는 진행 막대**를 깔았다(보유 ÷ 값). 살 수 있으면 금색으로 꽉 차고,
아니면 `737 더` 가 붙는다. '얼마나 더 모아야 하나'가 숫자 뺄셈이 아니라 눈에 보여야
제단에 다시 올 이유가 생긴다. 못 사는 칸을 예전처럼 알파 .45 로 눌러 버리면
정작 모으는 동안 볼 것이 안 보여서 .72 로 올렸다.

**제단 구슬이 곳간이다** — 보유 영혼에 따라 구슬과 후광이 자란다(4,000에서 최대).
숫자를 안 읽어도 얼마나 모았는지 보인다. 그 아래에 `지난 판 +663` 도 적는다.
이 값은 `Game.lastEarned` 에 따로 둔다 — 제단에 들어서는 순간 어트랙트 데모가
`Game.reset()` 을 불러 `soulsEarned` 를 지워 버리기 때문이다.

### 테스트

`tests/souls.js` — 처치가 두 배여도 영혼이 두 배가 되지 않는가(제곱근 배수 1.42) ·
최고의 판도 제단 절반을 못 사는가 · 그러면서 첫 칸은 두 판 안에 닿는가 ·
값이 레벨마다 오르는가 · 총액이 제자리인가 · 구입이 표시된 값만큼만 깎는가 ·
내역의 합이 지급액과 같은가.

옛 식으로 되돌려 돌려 봐서 실제로 잡히는 것을 확인했다 — 4개 항목이 실패하고
처치 배수가 정확히 2.00 으로 찍혔다.

## 20. 모바일 — 반쪽만 돌아가던 것

### 재 보니 두 가지가 막혀 있었다

**터치로는 직업 스킬과 아이템을 쓸 수 없었다.** 터치 이벤트는 가상 조이스틱(이동)만
처리했고, 스킬은 `SPACE`·`Shift`·우클릭, 아이템은 `Q`·`E` — 전부 키보드와 마우스였다.
폰으로 열면 직업의 절반과 소모품이 통째로 잠겨 있었다.

**세로로 들면 화면의 1/4 이 됐다.** 논리 해상도를 1280×720 으로 고정하고
`min(vw/W, vh/H)` 로 맞췄더니 390×844 짜리 폰에서 **390×219** 짜리 띠가 나왔다.

### 논리 해상도가 화면 비율을 따라간다

| 뷰포트 | 논리 해상도 |
|---|---|
| 390×844 (폰 세로) | 520×1126 |
| 844×390 (폰 가로) | 1410×652 |
| 820×1180 (태블릿 세로) | 520×748 |
| 1440×900 (노트북) | 1212×758 |
| 2560×1080 (와이드) | 1480×624 |

가로 화면은 **보이는 넓이**(1280×720)를 지킨다 — 16:10 이든 21:9 든 세계가 같은 양만큼
보여야 공평하다. 세로 화면은 그럴 수 없다. 넓이를 지키면 논리 폭이 650을 넘고,
그러면 390px 짜리 폰에서 13px 글자가 7px 로 찍혀 읽히지 않는다.
그래서 폭을 520 으로 먼저 정하고 높이를 늘린다 — **대신 세로로 들면 세계가 덜 보인다.
그건 화면 모양의 대가지 버그가 아니다.**

### 메뉴가 접힌다

- 직업 선택: 4열 → **2×2** (1,126px 이 필요해 세로 화면에서는 가운데 두 장만 보였다)
- 제단: 3열 → **1열**, 제단 돌은 배율로 줄여 세운다
- 레벨업 · 전직: 카드를 **세로로 쌓고 통째로 줄인다**. 내용이 빽빽해 다시 짜는 대신
  좌표계를 한 번 옮기는 쪽을 골랐다 — 마우스도 같은 계로 옮겨 판정한다
- 시작 화면: 버튼을 위아래로 쌓고 규칙을 두 줄로
- 자리가 없으면 참고 정보(조합 칩)를 접는다 — 가로로 든 폰은 높이가 652 뿐이다

### 터치 조작

오른쪽 아래에 스킬 · 아이템 버튼을 놓았다. 스킬 버튼은 **자원이 차는 만큼 안쪽이 차서**
언제 쓸 수 있는지 버튼만 봐도 안다. 조이스틱도 눈에 보이게 그렸다 — 여태 '보이지 않는'
물건이라 어디를 눌러야 하는지 알 수 없었다.

손가락은 여러 개다. `changedTouches` 를 하나만 보면 조이스틱과 버튼을 동시에 못 쓴다 —
식별자로 조이스틱 손가락을 따로 추적한다. 터치가 확인된 뒤에는 미니맵을 오른쪽 위로
올리고(버튼 자리와 겹친다) 아이템 칸을 왼쪽 아래로 옮긴다.

### 이번에도 조용히 죽을 뻔했다

카드 높이를 검사하는 코드에서 **아직 선언되지 않은 변수를 읽어(TDZ)** 가로로 든 폰에서
직업 선택 화면이 통째로 빈 화면이 됐다. 문법도 통과하고 다른 테스트도 전부 통과했다.
페이지 예외를 아무도 안 봤기 때문이다.

`tests/layout.js` 는 여섯 가지 화면 크기 × 일곱 화면을 돌면서
`panel()` 과 `fillText()` 를 감싸 **이번 프레임에 어디에 그렸는지**를 모으고,
전부 캔버스 안에 있는지 · 화면이 비어 있지 않은지 · 페이지 예외가 없는지 본다.
화면마다 좌표를 적지 않으므로 배치를 바꿔도 안 깨진다.
터치 버튼은 실제로 탭을 보내 스킬이 나갔는지 확인한다.

그 테스트가 처음 돌 때 자기 자신의 계측 오류도 두 개 냈다 — `panel` 에 좌표 변환을
안 먹여 멀쩡한 카드를 화면 밖이라 했고, 글자 기준선을 middle 로만 가정해 HUD 를
오탐했다. **재는 도구부터 고치고 나서** 남은 셋이 진짜였다.

### 덧붙여

`tests/regress-levelup-spam.js` 가 임시 폴더의 계측 스크립트에서 봇 소스를 읽고 있었다.
그 파일을 덮어쓴 날 게임은 멀쩡한데 테스트만 죽었다 — 봇을 `tests/bot.js` 로 들여왔다.
그러면서 이 테스트가 22초에 죽어 레벨 2 에서 끝나고 있던 것도 고쳤다.
'후반에 고를 게 없어지는가'를 보는 테스트가 후반에 닿지 못하고 있었다.
체력을 주어 15분을 완주하게 하니 레벨 24 · 레벨업 창 23회 · 회복 3장 0회가 나온다.

## 21. 마지막 이모지 — 인게임 HUD

메뉴를 전부 픽셀로 옮기고도 **화면에 그려지는 이모지가 열다섯 곳** 남아 있었다.
전부 인게임이었다 — 가장 오래, 가장 자주 보는 화면이 마지막까지 남았던 것이다.

`🛡 방벽` · `☠ 처치수` · `🔯 징표` · `🧪 광란` · `🔰 수호` · `❗ 미션` ·
`⛩️ 전직 가능` · `🐺 사냥개 무리`, 그리고 데이터에서 온 것들 —
무기 8 · 능력 9 · 소모품 5 · 속성 6 · 지형지물 3 · 구조물 4.

**레벨업 카드 한가운데의 52px 이모지가 제일 컸다.** 한 판에 스물몇 번 뜨는 화면이다.

### 판 22개를 더 떴다

`MENU_ICONS` 에 무기 여덟(단검 · 성역 · 플레일 · 마력탄 · 번개 · 성서 · 화염 · 낫),
능력 아홉, 소모품 다섯, HUD 표시(방패 · 해골 · 징표 · 물약 · 느낌표 · 제단 · 늑대)를 넣었다.
데이터 표에는 `icon` 옆에 `px` 를 달아 그리는 쪽이 그걸 쓰게 했다.

**다섯 개는 다시 그렸다.** 처음 판으로는 안 읽혔다 —
번개가 바람개비, 낫이 물음표, 해골이 빗, 느낌표가 빈 막대, 늑대가 고양이였다.

번개는 지그재그로, 낫은 초승달 날 + 대각선 자루로, 해골은 눈구멍을 비워서,
늑대는 주둥이를 뾰족하게.

각성 68종과 직업 특성은 저마다 판을 뜰 수 없다. 각성 색을 입힌 **문장(紋章) 하나**로
묶는다 — 이름과 설명이 바로 옆에 있으므로 그림이 종류를 구분할 필요가 없다.
그림이 해야 할 일은 '이게 무엇의 자리인지'를 알리는 것뿐이다.

이걸 그림으로 바꾸려면 문장을 쪼개고 폭을 재야 하는데 얻는 게 없다.

`.icon` 을 그리는 호출을 훑는다. 소스만 보므로 브라우저 없이 즉시 돈다.

## 22. 설정 — 여태 M 하나뿐이었다

설정이라고는 `M`(소리 전체 끄기) 하나였다. 음악만 끄고 효과음은 듣는다든가,
화면 흔들림이 불편하다든가, 피해 숫자가 어지럽다든가 — 어느 것도 손댈 수가 없었다.

| 항목 | 값 |
|---|---|
| 효과음 | 0~100% (4단계) |
| 음악 | 0~100% (4단계) |
| 화면 흔들림 | 끔 · 절반 · 기본 |
| 몬스터 이름표 | 끔 · 켬 |
| 피해 숫자 | 끔 · 켬 |
| 기록 지우기 | 두 번 눌러야 실행 |

### 슬라이더 대신 칸

값은 **칸**으로 보여준다. 슬라이더는 터치에서 잡기 어렵고 이 정도 항목에는 과하다.
칸을 직접 눌러도 되고 방향키로 옮겨도 된다 — 마우스 · 터치 · 키보드가 같은 것을 본다.

음량은 **막대**(찬 만큼 켜진다), 나머지는 **라디오**(고른 것 하나만 켜진다)로 나눴다.
처음엔 같은 규칙으로 그렸는데 음량 50% 인데 다섯 칸 중 셋이 켜져 60% 로 보였다 —
`0` 도 하나의 칸을 차지하고 있었기 때문이다. 음량은 0 을 칸에서 뺐다.

### 흔들림은 '읽는 곳'에서 곱한다

`cam.shake` 에 값을 넣는 곳이 **스물일곱 군데**다. 거기마다 배수를 곱하면
한 곳만 빠뜨려도 조용히 어긋난다. 화면을 실제로 옮기는 `frame()` 한 곳에서 곱한다.

### 갈 길이 없으면 설정이 아니다

`O` 키만으로 열게 두면 폰에서는 못 연다. 그래서 —
시작 화면에 **설정 버튼**, 전투 중에는 왼쪽 아래 **일시정지 버튼**(폰에는 `ESC` 가 없다),
일시정지 화면의 세 줄(계속 · 설정 · 포기하고 다시)을 전부 **누를 수 있게** 했다.
단축키는 각 줄 오른쪽에 같이 적는다.

### 조용히 죽기 쉬운 것

설정은 값이 바뀌고 저장도 되는데 정작 **쓰는 쪽이 안 보고 있으면** 화면에 아무 이상이
없다. 사용자만 '왜 안 되지' 한다. 그래서 `tests/options.js` 는 값이 아니라 **결과**를 잰다 —
소리가 실제로 났는지(오디오 노드 생성), 화면이 실제로 옮겨졌는지, 이름표와 숫자가
실제로 안 뜨는지, 다시 읽었을 때 그대로인지, 기록 지우기가 한 번에는 안 지워지는지.

여기서도 계측을 한 번 틀렸다. 흔들림을 재려고 `ctx.translate` 를 전부 셌더니
월드를 화면으로 옮기는 호출이 1,160px 로 잡혀 **꺼도 켠 것과 같은 값**이 나왔다.
한 프레임의 *첫* `translate` 만이 흔들림이다.

## 23. 해상도 — 판을 두 배로, 그리고 빛

레퍼런스 이미지를 놓고 "픽셀 수를 늘려 달라"는 요청. 먼저 지금 상태를 재고 시작했다.

**우리 스프라이트는 이미 레퍼런스가 말하는 「업그레이드 1」 크기였다** —
몹 32×32, 보스 64×64. 차이는 크기가 아니라 **명암 단계와 디테일**이었다.
우리는 색 3톤(기본·그늘·광택)에 평평한 실루엣이고, 레퍼런스는 방향광과 갑옷 조각이 있다.

### 좌표를 다시 쓰지 않고 두 배로

실루엣 12종이 전부 32 좌표계로 손으로 적혀 있다(`ell(g, 15.5, cy, ...)`).
숫자를 전부 다시 쓰는 대신 **원시함수가 배율을 먹게** 했다 — `mk` 가 격자에 `k` 를 기억하고
`ell · rect · line · eyes · shade` 가 들어온 좌표에 곱한다.

`ell` 은 확대된 크기에서 **다시 래스터화**하므로 픽셀을 두 배로 늘린 게 아니라
실제로 더 촘촘한 곡선이 나온다. 그게 해상도를 올리는 유일한 의미다.

격자를 직접 훑는 셋(`floor · floordeco · boom`)은 배율을 못 먹인다.
대신 그 함수들은 `S` 로 매개화돼 있어 최종 크기를 넘기면 그 크기로 알아서 그린다.

### 빛 — 여기가 진짜 차이다

**해상도만 올리면 같은 그림이 매끄러워질 뿐이다.** 늘어난 픽셀이 무언가를 담아야 한다.

왼쪽 위에서 빛이 온다고 보고, 각 픽셀에서 그 방향이 얼마나 열려 있는지로 밝기를 정한다.
열려 있으면 빛을 받는 면, 반대쪽이 열려 있으면 그늘진 면이다.

**마지막의 양자화가 핵심이다.** 연속 그라디언트로 두면 픽셀 아트가 아니라 에어브러시가 된다 —
`Math.round(f * 3) / 3` 으로 끊어야 색면이 생기고, 그래야 픽셀 아트로 읽힌다.

이펙트와 바닥 타일은 뺐다. 이펙트는 발광체라 방향을 가진 그림자가 붙으면 거짓이 되고,
바닥은 이어 붙는 그림이라 방향광이 들어가면 이음매가 드러난다.

그리고 인간형(좀비·괴수·사수·돌진자·방패병이 함께 쓴다)에 디테일을 얹었다 —
어깨 갑판 · 가슴 띠 · 허리 · 손 · **눈구멍을 먼저 파고 그 안에 빛을 둔다**. 얼굴이 생긴다.

### 화면 크기는 그대로, 밀도만

크기까지 같이 키우면 보스가 84 → 96px 로 커져 **게임 자체가 달라진다.**
이번에 바꾸려는 건 '더 선명한가'지 '더 큰가'가 아니다.

```
w × s = 예전 화면 크기 (32px 판은 32, 48·64px 판은 28)
64px 판 + s 0.5   → 화면 32px, dpr 2 에서 64 기기픽셀 = 판과 1:1
128px 판 + s 0.219 → 화면 28px(보스), 픽셀은 네 배로 촘촘
```

dpr 1 에서는 정확히 2:1 로 줄어든다. 둘 다 정수 배라 픽셀이 뭉개지지 않는다.

### 바닥이 유독 뭉개져 보였던 이유

스프라이트를 올리고 나니 바닥만 눈에 띄게 거칠었다. 원인은 타일 해상도가 아니라 **캐시**였다 —
`floorCv` 를 CSS 픽셀 크기로 깔아 두고 1:1 로 붙였는데, 고밀도 화면에서는
그 그림이 통째로 두 배로 늘어난다. 캐시를 판 해상도(2배)로 깔고 화면에는 줄여서 붙인다.

### 비용

| | 예전 | 지금 |
|---|---|---|
| 아틀라스 | 88KB (256×1984) | 234KB (512×3968) |
| 게임 파일 | 476KB | 651KB |
| 프레임(dpr2 · 적 200 · 카메라 이동) | 중앙 50.6ms | 중앙 52.2ms |

프레임은 **편차 안**이다(회차별 41~54 vs 45~54). 두 빌드를 번갈아 4회씩 재서 비교했다 —
한 빌드를 몰아서 재면 컨테이너 상태 변화가 그대로 결과가 된다.
실제로 처음엔 '정지가 이동보다 빠른' 결과가 나와 측정을 다시 짰다.

### 여기서 레퍼런스까지 남은 것

정직하게: **이건 레퍼런스가 아니다.** 절차적 생성으로 닿는 데까지 온 것이고,
남은 차이는 해상도가 아니라 **그려 넣은 것**의 차이다.

- 레퍼런스의 해골은 검과 방패를 들고 갈비뼈가 있다. 우리 인간형은 색 덩어리에 표식 몇 개다
- 레퍼런스의 바닥에는 돌 무늬 · 풀 · 꽃 · 빛웅덩이가 있다. 우리 바닥은 잡음 텍스처다
- 레퍼런스에는 림 라이트와 색 있는 환경광이 있다

여기서 더 가려면 둘 중 하나다 — **생성기에 실루엣을 한 종씩 손으로 더 그려 넣거나,
그린 스프라이트 시트를 받아 물리거나.** 해상도를 또 올리는 것으로는 더 나아지지 않는다.

## 24. A안 ① — 바닥을 손으로 다시 그렸다

23절의 "생성기에 실루엣을 한 종씩 손으로 더 그려 넣거나" 를 실제로 한 첫 번째 항목이다.
바닥부터 시작한 이유는 단순하다 — **화면의 7할이 바닥**이라 체감 변화가 가장 크다.

### 판석 (`floor`)

예전 바닥은 잡음 텍스처였다. 지금은 **줄눈이 어긋난 판석**(running bond)이다.

- 한 타일(128px)에 네 줄, 줄마다 판석 두세 장. 폭은 줄마다 다르게 나눈다
- 줄눈은 어두운 선 한 줄 + 그 아래 밝은 모서리 한 줄. 이 두 줄이 두께를 만든다
- 판석마다 톤이 다르되 **폭은 좁게**. 대비를 세우면 바닥이 TV 노이즈가 되어
  그 위의 몬스터와 싸운다 — 예전에 실제로 그랬고, 처음 다시 그렸을 때도 또 그래서
  '지하철 타일'이 됐다
- 금 하나, 이끼 몇 점, 잔돌 몇 알

**64px 격자가 보이던 문제.** 모든 타일이 x=0·y=0 에서 줄눈을 시작하니
넓게 깔면 격자가 그대로 드러났다. 줄마다 x 위상을, 타일마다 y 위상을 어긋냈다.
`px()` 가 좌표를 감싸므로 위상을 밀어도 이음매가 생기지 않는다.

### 장식 (`floordeco`) — 세 번 다시 그렸다

바닥 위에 **14%** 확률로 얹는다. 변종 네 가지: 이끼 · 풀포기 · 돌부스러기 · 뼈.

세 번 갈아엎으면서 배운 것이 이 절의 알맹이다.

**① 밝기.** 처음엔 풀을 '풀색'(`#4a6b3a`)으로, 꽃을 흰색으로 칠했다.
어두운 남색 바닥(밝기 28) 위에서 풀 끝 밝기가 95 였다 — 형광 스티커가 됐다.
지금은 전부 바닥 밝기의 2배 안이고 채도도 눌렀다.
**이 게임에서 채도가 높은 것은 몬스터와 이펙트뿐이어야 한다.**

**② 덩어리 대 낱개.** 두 번째 판은 장식 하나를 한 덩어리로 그렸다.
화면에서 타일은 64px 이고 장식은 그 안에서 20px 남짓인데, 그 크기에서 덩어리는
형체를 못 갖는다 — 이끼는 초록 손바닥이, 풀은 빗이, 뼈는 만화 개 뼈다귀가 됐다.
지금은 **작은 것 여럿을 흩는다.** 멀리서는 자국으로 뭉쳐 보이고 가까이서는 낱개가 보인다.

**③ 자리.** 세 개를 무작위 좌표에 두었더니 자주 겹쳐 한 덩어리가 됐다
(이끼 셋이 겹쳐 초록 반달, 뼈 셋이 겹쳐 화살촉, 뼈+두개골이 겹쳐 **열쇠**).
사분면을 하나씩 나눠 주고 그 안에서만 흔든다.

**④ 규칙적인 배치는 무작위보다 눈에 띈다.** 돌부스러기를 각도로 균등하게 흩었더니
고리가 보였고, 칸을 나눠 한 칸에 하나씩 두었더니 벽돌을 줄 맞춰 쌓은 것이 됐다.
줄을 어긋내고 크기를 제각각으로 두고 한둘은 아예 뺐다.

**⑤ 해시가 상관을 갖는다.** 얼룩을 극좌표(각도+반지름)로 흩었더니 낱알이
초승달 모양으로 줄을 섰다 — `k` 를 일정하게 올리면 이 해시는 각도도 같이 흐른다.
정사각형 안에 x·y 를 **축마다 다른 씨앗으로** 뽑고 원 밖이면 버리는 방식으로 바꿨다.

**⑥ 변종끼리도 구별돼야 한다.** 이끼(0)와 풀(1) 둘 다 '잎이 주인공'이면 같은 그림이다.
이끼는 얼룩이 주인공이고 싹은 곁들이, 풀은 그 반대로 잡았다.

### 계측

| | 값 |
|---|---|
| 장식이 붙는 비율 | 14.0% |
| 배치 자기상관 (1.0 이 무작위) | 최대 1.08 |
| 변종 분포 | 25 / 25 / 25 / 25 % |
| 바닥 판 다시 칠하기 (308장) | 0.4ms |
| 아틀라스 | 240KB (512×3968) |

바닥 다시 칠하기는 아틀라스에서 긁어 붙이는 것뿐이라 밀도를 올려도 값이 오르지 않는다.
카메라가 한 타일 넘어갈 때만 일어난다.

### 남은 것

A안의 다음 순서는 **주인공 → 보스 → 일반 몹**이다. 가장 오래 보는 것부터다.

## 25. A안 ② — 주인공을 64칸에 다시 그렸다

### 왜 해상도가 올랐는데 그림은 그대로였나

23절에서 판을 32→64px 로 올렸는데도 주인공은 별로 달라 보이지 않았다. 이유는 간단하다 —
**좌표를 32칸에 적고 원시함수가 2배로 늘리고 있었다.** 모든 형태가 짝수 픽셀에만 놓이니
결과는 '픽셀이 큰 32px 그림'이었다. 확대해 보면 투구가 그냥 네모다.

그래서 `NATIVE` 라는 갈래를 하나 더 뒀다. `RAW`(바닥 타일)와 달리 **빛 처리는 그대로 받되**,
좌표계만 최종 해상도(64칸)로 바꾼다. 투구의 볼가리개, 갑옷의 능선, 무릎 보호대,
칼의 혈조 — 전부 홀수 픽셀에 놓여야 나오는 것들이다.

```js
const NATIVE = new Set(['hero']);
CURK = (raw || nat) ? 1 : SCALE;
const g = SIL[def.shape](f, (raw || nat) ? S : def.h, def);
const lm = (def.fx || raw) ? null : lightMap(g);   // NATIVE 는 빠지지 않는다
```

### 규칙 하나: 몸을 조각으로 나눈다

판 하나를 통째로 칠하면 앞치마가 되고, 다리를 막대 하나로 두면 장화 신은 막대가 된다.

- 갑옷 = 가슴판 · 허리띠 · 치마판 (세 조각)
- 다리 = 허벅지 · 무릎 보호대 · 정강이 · 장화 (네 조각)
- 무기 = 자루 끝 · 손잡이 · 코등이 · 날 · 혈조 (다섯 조각)

**조각 사이의 선이 형태를 만든다.** 그리고 손으로 넣는 광은 전부 조각의 위·왼쪽 모서리에,
그늘은 오른쪽·아래에 놓는다 — `lightMap` 과 같은 방향이다. 어긋나면 빛이 두 개로 보인다.

```js
const plate = (x0, y0, x1, y1, base, hi, lo) => { ... };  // 이 규칙을 함수로 굳혔다
```

재질마다 세 단계를 준다. 두 단계로는 판이 접히지 않는다.
`M/m/e`(강철) · `L/l/d`+`u`(가죽) · `A/G/a`(직업색) · `S/s`(살).

### 여기서도 틀린 것들

**① 어깨판이 몸통과 같은 색이면 통째로 사라진다.** 성기사의 어깨판이 그랬다.
밑에 어두운 타원을 먼저 깔면 테두리가 삐져나와 판을 떼어 놓는다.

**② 굵은 한 획으로 눕힌 깃털은 바나나가 된다.** 가늘어지는 세 가닥으로 나눴다.
(위로 세우면 64칸 판을 넘어 잘린다 — 예전 그림이 그랬다.)

**③ 수염이 얼굴을 다 덮으면 갈색 덩어리가 된다.** 전사의 얼굴이 그랬다.
턱 아래만 남기고 눈과 콧수염을 드러냈다.

**④ 두건 꼬리를 옆으로 뻗으면 새 부리가 된다.** 짧게, 아래로 늘어뜨린다.

**⑤ 왼손 무기를 오른손과 같은 각도로 두면 T 자세가 된다.** 추적자의 왼손 단검을
역수로 잡게 했다.

**⑥ 32px 에서 직업이 읽히려면 직업색이 넓은 면에 있어야 한다.** 추적자는 두건·조끼·바지가
전부 갈색이고 초록은 가는 띠 하나뿐이라 갈색 덩어리였다. 두건을 직업색으로 돌렸다.
**다만 직업색 원본(`#8ef0b0`)을 그대로 칠하면 민트색 머리카락이 된다** —
천은 어두운 면이 기본이고 밝은 색은 빛 받는 모서리에만 온다.

**⑦ 소매를 로브와 같은 색으로 두면 팔이 없다.** 마법사가 그랬다.

**⑧ 어두운 판은 그냥 두면 상자다.** 전사의 가슴에 사슬갑옷 무늬를 넣어 깼다.

### 크기는 그대로

`s = 32 / 64 = 0.5`. 화면에서 32px, 예전과 같다. 바뀐 것은 밀도뿐이다 —
23절과 같은 원칙이다. 크기를 같이 키우면 게임 자체가 달라진다.

## 26. A안 ③④ — 보스와 일반 몹

주인공과 같은 처방이다. `NATIVE` 에 넣어 최종 해상도(보스 128 · 몹 64)에 직접 그리고,
재질을 나누고, 부위 사이에 어두운 경계를 둔다. 여기서는 그 과정에서 나온
**일반화할 수 있는 규칙**만 적는다.

### 규칙 ①: 재질마다 세 단계 이상

예전 보스와 몹은 전부 이랬다 — 도형 하나를 `def.color` 로 칠하고, 아래 절반을 어둡게 하고,
밝은 점 하나를 찍는다. 확대해 보면 색종이다. 슬라임은 초록 달걀, 박쥐는 보라색 콧수염,
보스는 오려 붙인 나방이었다.

지금은 프레임마다 이 단계를 자동으로 만든다:

```
C = 색 + 흰색 34%     밝은 면
B = def.color         기본
D = 색 + 검정 30%     그늘
c = 색 + 검정 58%     깊은 그늘
Q/q = 채도를 죽인 두 단계 (갑옷)
F/E = 뼈 — 유일한 중립색
```

**갑옷을 진짜 강철로 두면 보스 넷이 다 같아 보인다.** 그래서 색은 남기고 채도만 죽였다.

### 규칙 ②: 부위 사이에 어두운 경계

재질을 나눈 것만으로는 부족했다. 보스의 갑옷이 전부 `q` 한 톤이라
어깨판·팔·몸통이 다시 한 덩어리가 됐다 — **팔이 통째로 사라졌다.**

```js
const edged = (x0,y0,x1,y1, base,hi,lo, m=2) => {
  rect(g, x0-m, y0-m, x1+m, y1+m, 'O');   // 어두운 판을 먼저 넓게
  plate(g, x0,y0,x1,y1, base,hi,lo);       // 그 위에 판
};
```

같은 색 판끼리 붙을 때 이것 하나로 해결된다. 주인공의 어깨판도 같은 처방이었다.

### 규칙 ③: 뼈에는 예산이 있다

뼈(`F`/`E`)는 이 그림들에서 **대비가 가장 센 색**이다.
보스에서 뿔·어깨가시·발톱·엄니 네 군데에 다 쓰고 전부 바깥 모서리에 두었더니 벌레가 됐다.
사냥개에서 등가시를 뼈로 넷 세웠더니 개가 아니라 벌레가 됐다.

지금은 **한 생물에 한두 군데**만 쓴다 — 보스는 뿔과 엄니, 사냥개는 이빨만.
그 대신 이빨이나 발톱 하나가 생물을 '색 덩어리'에서 '짐승'으로 바꾼다.

### 규칙 ④: 위엄은 비례에서 온다

보스의 어깨와 팔을 넓힐수록 정사각형이 됐고, **정사각형은 크기와 무관하게 위엄이 없다.**
위는 좁게(뿔), 아래는 넓게(망토) — 삼각형이라야 선다.
지금 가장 넓은 곳은 망토 아랫단이다.

### 형태별로 걸렸던 것들

| | 잘못 읽힌 것 | 원인 | 고침 |
|---|---|---|---|
| 보스 뿔 | 치켜든 팔(V 자) | 위로만 뻗음 | 밖으로 나갔다 끝에서 아래로 말림 |
| 보스 어깨가시 | 뿔 한 쌍이 더 | 길고 뾰족함 | 짧고 뭉툭하게, 갑옷색으로 |
| 슬라임 | 흰 배를 가진 달걀 | 아래 빛샘이 넓고 흼 | 좁게, `C` 로 |
| 슬라임 눈 | 선글라스 | `eyes()` 가 네모 | 타원으로 직접 |
| 슬라임 입 | 웃는 얼굴 | 입꼬리가 위 | 내림 — 죽이러 오는 것이 웃으면 안 된다 |
| 박쥐 날개 | 몸과 한 덩어리 | 막이 몸과 같은 색 | 막을 `c` 로 |
| 사냥개 | 널빤지를 진 덩어리 | 굵은 꼬리를 45° 로 세움 | 가늘게, 눕힘 |
| 사냥개 | 다리가 기둥 둘 | 앞뒤 다리가 겹침 | 먼 쪽을 어둡게, 무릎에서 꺾음 |
| 좀비 | 초록 유령 | 몸통이 한 덩어리 | 팔다리를 어두운 경계로 떼어 놓음 |

### 비용

| | 예전 | 지금 |
|---|---|---|
| 아틀라스 | 88KB → 240KB(바닥) | 300KB |
| 게임 파일 | 651KB | 813KB |

크기(`s`)는 하나도 바꾸지 않았다. 몹 28px · 보스 84px · 주인공 32px — 전부 예전 그대로다.
바뀐 것은 밀도뿐이다.

## 27. A안 ⑤ — 지형 12종

스프라이트를 전부 64·128칸으로 올리고 나니 **지형만 눈에 띄게 거칠어졌다.**
지형은 아틀라스가 아니라 캔버스에 직접 그린다(`PIX = 3` 격자). 판이 아니라 코드라
'해상도를 올린다'가 성립하지 않는다 — 대신 **톤 단계를 늘리고 면을 갈랐다.**

### 톤을 셋에서 다섯으로

예전에는 겉(`dark`) · 몸통(`color`) · 윗면(`lit`) 셋뿐이었다. 지금은 다섯이다.

```js
deep = 색 + 검정 74%     // 줄눈 · 금 · 구멍
dark = 색 + 검정 50%     // 그늘 면
mid  = 색 + 검정 22%     // 몸통
lit  = 색 + 흰색 28%     // 빛 받는 면
hot  = 색 + 흰색 55%     // 정수리 광
BONE = '#ded2b4'         // 중립색 — 한 지형에 한 군데만 (스프라이트와 같은 규칙)
```

빛은 스프라이트와 **같은 방향(왼쪽 위)** 이다. 어긋나면 화면에 빛이 두 개 있는 것처럼 보인다.

### 형태별로 걸렸던 것

| | 잘못 읽힌 것 | 고침 |
|---|---|---|
| 바위 (전체의 6할) | 회색 자갈 | 윗면·왼쪽 면·오른쪽 그늘·정수리 광 + 금 + 발치 부스러기 |
| 석벽 | 격자 그린 상자 | 돌마다 톤을 흔들어 쌓는다 — 한 톤이면 상자다 |
| 폐허 | 도시 스카이라인 | 낮은 벽 + **아치 문** + 이 빠진 윗단. 문 하나로 '건물이었던 것'이 된다 |
| 수정 기둥 | 물방울 | 면을 갈라 조각 셋 (왼쪽 밝음 / 오른쪽 어두움) |
| 가시덤불 | 이끼 매트 | 얽힌 줄기 + 줄기에 돋은 가시 + 붉은 열매 |
| 고목 | 갈퀴 / 손 | 가지를 **양쪽**으로, 뿌리와 옹이와 구멍 |
| 석상 | 소화전 → 꽂힌 칼 | 두건과 모아 쥔 팔, 그리고 옷폭을 넓혀서 |
| 첨탑 | 보라색 막대 | 네모 기둥의 두 면 + 피라미드 꼭대기 + 새겨진 룬 |
| 늪 | 거의 안 보임 | 테두리를 밝게, 갈대를 세워 |

원통(기둥·첨탑)은 **'왼쪽 밝음 → 오른쪽 어두움' 한 줄만 넣어도 둥글게 선다.**
반대로 네모난 것(석벽)은 면마다 톤이 같으면 아무리 줄눈을 그어도 상자로 남는다.

### 비용

없다. 그리는 도형 수는 늘었지만 전부 `pxR`/`pxLineQ` 로 한 경로에 모아 칠하므로
`fill()` 횟수는 지형 하나당 여남은 번 수준 그대로다.

## 28. A안 ⑥ — 이펙트: 색이 아니라 형태로 구별한다

화면에서 **가장 자주, 가장 많이** 보이는 것이 타격 이펙트다. 그런데 예전에는
속성 여섯이 **전부 같은 별표**였고 색만 달랐다. 무엇에 맞았는지가 안 읽혔다.

색만으로 구별하면 색맹인 사람에게는 구별이 **없다**. 형태가 먼저다.

### 여섯 형태

| 속성 | 형태 | 왜 |
|---|---|---|
| 물리 | 엇갈린 베기 자국 | 별표는 '터졌다'이지 '베였다'가 아니다. 무기가 지나간 길이 보여야 한다 |
| 화염 | 위로 오르는 불꽃 혀 | 불은 방향이 있다 — 사방으로 균등하면 불이 아니다 |
| 냉기 | 여섯 갈래 결정 | 눈송이는 여섯이라야 눈송이다. 잔가지까지 |
| 폭풍 | 갈래 번개 | 곧은 선은 번개가 아니다. 꺾여야 번개다 |
| 신성 | 세로가 긴 빛기둥 십자 | 정십자는 표식이지 빛이 아니다 |
| 흡혈 | 튄 자국 | 날아간 방향으로 늘어나고, 꼬리는 방울 쪽이 굵다 |

여기서도 두 번 틀렸다 —
**호 둘을 마주 보게 놓았더니 괄호(`) (`)가 됐고**, 엇갈려야 벤 자국이 된다.
**정원 방울에 곧은 꼬리를 달았더니 분자 모형이 됐다.**

획은 **가운데가 굵고 양 끝이 가늘어야** 획이다. 굵기가 균일하면 막대다.

### 폭발도 가장자리로 구별한다

폭발은 형태가 다 고리라 바꿀 수 없다. 대신 **가장자리의 성격**을 속성마다 달리했다 —
얼음은 각지고(진폭 .16 · 주기 6), 불은 뭉실하고(.13 · 9), 물리는 매끈하다(.08).
그 위에 냉기는 서리 가시, 신성은 빛살, 폭풍은 고리를 가로지르는 방전을 얹는다.

### 탄알 — 층을 얹지 않고 옮긴다

화면에 탄이 300발일 때 층을 하나 더 얹을 수는 없다(`pxDisc` 는 탄 하나당 `fill()` 두 번).
그래서 **있는 층을 옮겼다** — 안쪽 밝은 층을 한가운데 두면 과녁이고, 왼쪽 위로 밀면 구슬이다.
값은 그대로다. 빛 방향은 스프라이트·지형과 같은 왼쪽 위.

### 규격 변경

`atlas-spec.json` 의 `fx_*` 항목에 `el`(속성) 필드를 넣었다. 실루엣 함수가 그것으로 갈라진다.
`hit`·`cast` 는 `NATIVE` 로 옮겨 64칸에 직접 그린다.

화면 크기는 그대로다 — `spawnFx` 가 `f.scale = px / fr.w` 로 잡으므로
판 크기를 바꿔도 보이는 크기는 변하지 않는다.

## 29. A안 ⑦ — UI: 화면에 둥근 모서리를 남기지 않는다

바닥부터 이펙트까지 전부 픽셀로 맞추고 나니 **UI 만 웹 페이지처럼** 보였다.
칸이라는 칸은 전부 `roundRect` 에 1.5px 선 하나였다 — 가장자리가 부드러워
게임의 다른 모든 것과 재질이 어긋났다.

### panel() 하나가 화면 전부를 바꾼다

직업 카드 · 레벨업 카드 · 전직 카드 · 제단 줄 · 설정 줄 · 일시정지 · 결과 —
**열두 군데가 전부 같은 함수를 쓰고 있었다.** 그래서 그 함수만 고쳤다.

```
바깥 검은 테 (1칸) → 상태색 테 (1칸) → 안쪽 판
그 위에 위·왼쪽 광 1칸, 아래·오른쪽 그늘 1칸
모서리는 둥글리는 대신 계단으로 깎는다
```

빛 방향은 스프라이트·지형·이펙트와 같은 왼쪽 위다.
**상태색을 1px 선이 아니라 한 칸 띠로 두니 선택된 카드가 훨씬 분명해졌다** —
같은 색인데 면적이 세 배가 된다.

### 하나라도 남으면 그것만 눈에 띈다

`panel` 만 고치고 보니 배지 · 조합 줄 · HUD 막대 · 무기 슬롯 · 미니맵 테가
전부 둥근 채로 남아 **오히려 더 어긋나 보였다.** 21군데를 전부 `pxChip` 으로 옮겼다.
`roundRect` 폴리필도 지웠다 — 쓰는 곳이 하나도 없다.

`stroke()` 는 못 쓴다. 격자 모서리는 사각형 여럿의 합집합이라 선을 두르면
사각형마다 테두리가 생긴다. 그래서 `pxChip(x,y,w,h,fill,stroke)` 가
**바깥을 stroke 색으로 칠하고 안쪽을 fill 로 덮는** 방식으로 테두리를 만든다.

### 카드 높이를 내용에서 계산한다

레벨업 카드는 높이가 356 고정이었다. 조합 줄이 없는 카드는 **아래 절반이 통째로 비어**
'내용을 채우다 만 판'으로 보였다. 석 장이 높이를 공유하므로 가장 큰 것에 맞춘다:

```js
let maxRows = 0;
for (const c of Game.choices) maxRows = Math.max(maxRows, comboRowsFor(c).length);
const bottom = maxRows ? 292 + (Math.min(2, maxRows) - 1) * 30 + 13 : 276;
const ch = bottom + 30;                       // [번호] 자리를 남긴다
```

그러려면 조합 줄을 **그리기 전에** 알아야 해서 `comboRowsFor()` 로 빼냈다.
처음엔 `+30` 을 빼먹어 조합 칩과 `[1]` 이 겹쳤다.

### 그 밖에

- **막대**(체력 · 직업 자원)가 `fillRect` 두 번이라 종이처럼 납작했다.
  틀을 두르고 채움의 윗줄만 밝게 하니 같은 값으로 두께가 생긴다 (`pxBar`).
- **결과 화면에 판이 없었다.** 어둡게 덮어도 세계가 비쳐 주인공의 후광이
  숫자 한가운데를 지나갔다. 읽을 곳에는 바닥이 있어야 한다.

### 메뉴 글리프 일곱 개가 다른 것으로 읽히고 있었다

34개를 7×7 로 늘어놓고 하나씩 읽어 보니 일곱이 틀렸다.

| | 실제로 읽힌 것 | 고침 |
|---|---|---|
| 검 · 단검 | **촛불** (날이 심지, 코등이가 받침) | 눕힌다 — 대각선이라야 검이다 |
| 낫 | **P** → (한 번 더 틀려) **Γ** | 초승달을 열어 두고 자루를 아래로 |
| 화염 | 젤리 덩어리 | 끝을 뾰족하게, 밑을 갈라서 |
| 힘 | 네 발 짐승 → (한 번 더 틀려) 전나무 | 폭이 같은 갈매기 둘을 띄워서 |
| 잎 | 깃발 → (한 번 더 틀려) 구름 | 기운 아몬드 + 잎맥 + 줄기 |
| 물약 | 덩어리 | 목을 좁게, 몸을 넓게 |

`drawMenuIcon` 은 `rows.length` 로 격자를 읽으므로 글리프마다 크기를 달리해도 된다.
그래도 7×7 을 지켰다 — 글자 옆에 붙는 자리가 있어서 키우면 겹친다.
**7칸에서 안 읽히면 모양을 바꿔야지 칸을 늘릴 일이 아니다.**

## 30. 빛 — 픽셀 수로 설명되지 않는 차이

레퍼런스 그림과 우리 화면을 나란히 놓고 보면, 차이의 상당 부분이 **해상도가 아니다.**
큰 것 셋을 꼽으면 이렇다.

| | 우리 | 레퍼런스 | 픽셀 수 문제인가 |
|---|---|---|---|
| 조명 | 화면 전체가 같은 밝기 | 화톳불 옆이 밝고 구석이 어둡다 | **아니다** |
| 화면 속 캐릭터 크기 | 폭의 2.5% (32px) | 폭의 8% 안팎 | **아니다** (카메라 문제) |
| 캐릭터에 그려 넣은 것 | 절차 생성의 한계 | 손으로 그린 시트 | 그렇다 |

이 절은 첫 번째를 다룬다. 셋 중 **비용 대비 효과가 압도적으로 크다** —
그림을 한 픽셀도 다시 그리지 않고 공간이 생긴다.

### 방식

화면 1/4 크기 판에 어둠을 깔고, 광원 자리를 `destination-out` 으로 지워 구멍을 낸 뒤,
그 판을 **보간 없이** 확대해 월드 위에 덮는다.

**1/4 로 그리는 것이 핵심이다.** 원본 해상도로 그리면 매끈한 그라디언트가 되어
격자에 맞춘 나머지 전부와 재질이 어긋난다. 낮은 해상도에서 그린 뒤 늘리면 빛도 계단이 된다 —
스프라이트의 `lightMap` 을 3단계로 끊은 것과 같은 이유다.

### 어둠을 걷는 것만으로는 불이 안 된다

구멍을 뚫으면 그 자리는 **원래 밝기**일 뿐이다. 불은 색을 얹어야 광원이 된다.
그래서 같은 판을 지우고 한 번 더 써서, 화톳불·수정·폭발 자리에 속성색을 `lighter` 로 더한다.

### 여기서 틀린 것

**① 타격 이펙트를 광원으로 두면 화면이 하얗게 날아간다.** 후반에는 한 프레임에 백 개가 뜬다.
폭발만, 그것도 여덟 개까지로 잘랐다.

**② 정거리 감쇠(0→.5→1)는 가장자리에 동그란 테를 남긴다.** 안쪽은 완만하고
바깥으로 갈수록 빨리 죽게 단계를 넷으로 늘렸다.

**③ 계측을 두 번 잘못 짰다.** `frame()` 전체를 재니 `update()` 가 값을 삼켜
'조명 켠 쪽이 더 빠르다'는 결과가 나왔다. `drawLighting()` 만 직접 재야 한다.

### 계측

| | 값 |
|---|---|
| `drawLighting()` (적 211마리) | 중앙 **1.00ms** · 상위10% 1.20ms |
| 프레임 예산(60fps) 대비 | 6% |

**끌 수 있게 했다.** 어두우면 못 보겠다는 사람이 반드시 나오고, 이건 분위기지 정보가 아니다.
설정에 `조명 — 끔 / 약하게 / 기본`.

## 31. 캐릭터 크기 · 소품 밀도 · 몹 변주

30절에서 "레퍼런스와의 차이 중 픽셀 수로 설명되지 않는 것"을 셋 꼽았다.
①조명은 30절에서 했다. 여기서 ②크기와, 그 밖에 눈에 띄게 비어 있던 둘을 채운다.

### ② 보이는 크기와 맞는 크기를 나눈다

레퍼런스의 기사는 화면 폭의 8% 안팎인데 우리는 2.5% 였다.
**판을 64·128칸으로 올려 놓고도 조밀함이 잘 안 보였던 이유가 여기 있다** —
32px 안에서는 아무리 촘촘해도 촘촘함이 보이지 않는다.

카메라를 당기면 캐릭터는 커지지만 몰려오는 떼가 덜 보인다. 그건 이 장르의 재미를
깎는 거래다. 그래서 **카메라는 그대로 두고 보이는 크기만** 키웠다 (`CHAR_SCALE = 1.25`).

충돌 반경(`r`)은 건드리지 않았다. 이건 '보이는 크기'지 '맞는 크기'가 아니다 —
그림이 판정보다 조금 큰 쪽은 관대한 방향이라 문제가 되지 않는다(그 반대가 문제다).

**몹 그림자도 같이 넣었다.** 예전에는 주인공에게만 있었다. 없으면 몹이 바닥에
붙지 않고 떠 있다. 나는 것(박쥐·유령)은 그림자가 작고 아래로 떨어져 있어야
'떠 있다'가 읽힌다.

### 몹 변주 — 색이 아니라 모양으로

인간형 다섯(좀비·거구·궁수·돌격병·방패병)이 **색만 다르고 실루엣이 똑같았다.**
화면에 200마리가 있는데 '무엇이 오는지'가 색으로만 구별되면 난전에서는 못 읽는다.
이펙트에서 배운 것과 같은 규칙이다 — **위험한 것과 안 위험한 것은 모양이 달라야 한다.**

뼈대는 공유하고 붙는 것만 다르다:

| | 붙는 것 |
|---|---|
| 좀비 | 맨몸 · 드러난 갈비뼈 · 손톱 |
| 거구 | 어깨 너비 13→16 · 근육 결 · 큰 주먹 |
| 궁수 | 앞으로 뻗은 활 · 등에 멘 화살통 · 두건 |
| 돌격병 | 뿔투구 · 뒤로 젖힌 팔 · 앞으로 숙인 머리 |
| 방패병 | 큰 방패(십자 무늬) · 챙 달린 투구 |

### 소품 밀도 — 바닥 장식을 두 겹으로

첫째 겹은 자연(이끼·풀·돌부스러기·뼈), **둘째 겹은 유물**(무늬 판석·물웅덩이·부서진
널판·덩굴). 레퍼런스 바닥에는 무늬 박은 판석과 부서진 널판이 있고 우리는 풀만 있었다.

| | 값 |
|---|---|
| 첫째 겹 | 14.2% |
| 둘째 겹 | 11.0% |
| 겹침 | 1.5% (독립이면 1.6% — 둘은 서로 무관하다) |
| **무언가 있는 칸** | **14% → 23.7%** |

지형에도 둘을 더했다 — **나무 상자**(부술 수 있다)와 **등불**(지나갈 수 있고,
조명 체계의 광원이다). 바위 비중을 62%→52% 로 덜어 자리를 만들었다.

### 여기서 또 틀린 것

- **물웅덩이에 흰 테를 둘렀더니 접시가 됐다.** 그다음엔 나란한 줄 두 개를 그어
  등호(`=`)가 됐다. 윤은 하나만, 짧게, 비스듬히.
- **널판을 흙색으로 두니 바닥에 묻혔고**, 돌부스러기색(차가운 회색)으로 바꾸니
  이번엔 뼈로 보였다(둘째 겹에 이미 뼈가 있다). 나무는 따뜻해야 나무다.
- **좌표를 해시로만 뽑으니 넷이 한자리에 겹쳐 사다리가 됐다.** 24절에서 이미 겪은
  것인데 또 했다 — 사분면을 나눠 주는 것으로 끝난다.
- **상감 판석을 크게 그리고 모서리를 밝게 둘렀더니 바닥에 놓인 상자 뚜껑이 됐다.**
  박아 넣은 것은 그림자도 테두리도 없다. 톤 차이만 아주 조금.
- **상자를 세로로 길게 그렸더니 발판이나 교수대로 보였다.** 상자는 대체로 정육면체다.

## 32. 이펙트 2차 — 캔버스로 그리는 쪽

28절에서 아틀라스 이펙트(타격·폭발·시전)를 속성별 형태로 갈랐다.
남은 것은 **캔버스로 직접 그리는 쪽** — 파티클 · 발사체 · 참격 · 파동이다.
이쪽은 아직 "도형 하나를 알파로 흐리게" 수준이었다.

### 파티클 — 색종이 조각에서 파편으로

예전 파티클은 전부 **같은 크기의 네모**가 사방으로 똑같이 퍼졌다가 제자리에서 사라졌다.
셋을 더했다.

**① 줄어든다.** 수명이 줄면 크기도 준다. 끝까지 같은 크기면 '꺼지는' 게 아니라
'사라지는' 것이다.

**② 중력.** 위에서 내려다보는 화면이지만 파편이 아래로 처지면 무게가 생긴다 —
실제 물리가 아니라 눈이 그렇게 읽는다.

**③ 자국(streak).** 빠른 것은 진행 방향으로 늘어난 자국을 남긴다.

**④ 방향.** 타격 불티가 사방으로 똑같이 퍼지면 어디서 맞았는지가 안 보인다.
`damageEnemy` 는 이미 `fromX/fromY` 를 안다 — 맞은 반대쪽으로 부채꼴로 튀게 하면
**같은 파티클 두세 개로 '이쪽에서 왔다'가 읽힌다.**

**⑤ 모든 처치에 파편.** 예전에는 정예·희귀만 있었고 보통 몹은 소리 없이 사라졌다.
한 판에 수천 번 일어나는 일에 아무 되먹임이 없었던 셈이다.

> 다만 개수를 넉넉히 잡으면 안 된다. 처음에 5개씩 뿌렸더니 파티클 풀(500)이
> **467/500** 로 포화됐다. 그러면 정작 타격 불티가 자리를 못 얻는다. 셋으로, 짧게.
> (계측해 보니 포화 자체는 그 전부터 있던 것이었다 — 내 변경이 원인은 아니었다.)

### 발사체 꼬리

탄에 꼬리가 없으면 **움직이는 물체가 아니라 떠 있는 점**으로 보인다.

이력을 배열에 저장하면 탄 300발 × 프레임마다 배열이 커진다. 대신 **속도 방향으로
뒤에 점점 작아지는 원 셋**을 찍는다. 멈춘 탄(속도 40 미만)에는 안 붙인다.

**여기서 틀렸다 — 작아지기만 하고 흐려지지 않으면 꼬리가 아니라 구슬 목걸이가 된다.**
알파를 함께 떨어뜨려야 하나의 자국으로 읽힌다.

### 참격의 심지 · 파동의 앞날

- **참격**: 굵은 호 안쪽에 얇고 밝은 호를 하나 더. 한 겹이면 색칠한 부채꼴이고,
  두 겹이면 '지나간 길'이 된다. (레퍼런스 그림의 참격이 이 구조다.)
- **파동**: 가장 바깥 한 줄만 희게 — 여기가 부딪히는 자리다.
  그리고 뒤에 흐린 테를 하나 더 남겨 '지나갔다'가 보이게.

### 비용

같은 시나리오(추적자 · 4분 · 적 ~180)로 직전 커밋과 **번갈아 4회씩** 쟀다.

| | 중앙 | 회차별 |
|---|---|---|
| 전 | 8.8ms | 7.9 8.5 8.8 9.6 |
| 후 | 10.4ms | 8.3 8.4 10.4 10.4 |

**정직하게: n=4 이고 범위가 겹친다**(전 최대 9.6 vs 후 최소 8.3).
중앙값 차이 ~1.6ms 가 전부 이펙트 탓이라고 단정할 수 없다.
확실한 것은 둘 다 60fps 예산(16.7ms) 안이라는 것뿐이다.

## 33. 아이콘 — 유일하게 뒤처져 있던 것

실제 플레이 보고: **"스킬 아이콘이랑 아이템 아이콘이 업그레이드가 아니라 다운그레이드 되었어."**

맞는 지적이었다. 다른 것은 전부 조밀해졌는데(주인공 64칸 · 보스 128칸 · 지형 5단계)
아이콘만 **7칸 3단계**로 남아 있었다. 레벨업 카드에서는 한 칸이 화면 8px 이다 —
**같은 화면의 주인공 스프라이트 픽셀보다 여덟 배 굵다.** 상대적으로 뒤처진 게 맞다.

### 왜 아틀라스에 넣지 않는가

아이콘은 **호출할 때마다 색이 다르다** — 속성색·직업색·강조색·회색(못 사는 칸).
구운 그림은 색을 갈아입지 못한다. 그래서 색이 아니라 '단계'를 적는 격자로 남긴다.
대신 **칸을 7→16 으로, 단계를 3→5 로** 올렸다.

```
'0' 윤곽 · '1' 그늘 · '2' 몸통 · '3' 빛 · '4' 광
```

### 화면 크기는 그대로

스프라이트의 `s` 와 같은 규칙이다. 기준은 예전 격자인 7칸:

```js
function iconCell(rows, cell) { return Math.max(1, Math.round(cell * 7 / rows[0].length)); }
```

덕분에 **7칸과 16칸 글리프가 섞여 있어도 호출부는 아무것도 몰라도 된다.**
34개를 한꺼번에 갈아엎지 않고 하나씩 옮길 수 있었다.
`iconText` 만 폭을 물어보게 고쳤다(`menuIconW`) — 안 그러면 글자와 겹친다.

### 손으로 안 적고 생성한다

7칸도 일곱 개가 다른 것으로 읽혔다(촛불 · P · 젤리 · 짐승 · 깃발 · 덩어리).
**16칸을 34개 손으로 타이핑하면 더 틀린다.** `art/make-icons.js` 가
스프라이트와 같은 원시함수(`ell`/`rect`/`line`)로 그리고, 윤곽과 음영을 자동으로 얹는다.
빛 방향은 왼쪽 위 — 스프라이트·지형·이펙트와 같다.

생성기라 고쳐 그리기가 빠르다. 실제로 세 바퀴 돌았다.

| | 잘못 읽힌 것 | 몇 번 만에 |
|---|---|---|
| 불꽃 | 천막 → 풍선 | 3번 |
| 낫 | 막대인간 → 곡괭이 → 7 자 | **4번** |
| 날개 | 쐐기 → 고깃덩이 | 3번 |
| 장화 | L 자 | 2번 |
| 잎 | 총 | 2번 |
| 채찍 | 지그재그(번개) | 2번 |

낫에서 배운 것: **초승달은 '선'이 아니라 '면'이다.** 호를 그어서는 안 되고,
큰 원에서 작은 원을 빼야 한다. 그리고 자루를 날 한가운데 두면 곡괭이가 된다.

불꽃에서 배운 것: 아래로 넓어지는 삼각형은 천막이고, 가운데가 제일 넓으면 풍선이다.
**불은 아래쪽 3/4 지점이 가장 넓고 밑동이 오목하다.**

## 34. 아이콘 2차 — 16칸으로도 모자랐다

7칸에서 16칸으로 올린 다음에도 제보가 왔다. **"스킬 아이콘의 픽셀이 너무 갯수도 적고 세밀함이 없어."**

맞는 말이었다. 레벨업 카드의 아이콘은 화면에서 한 변이 64px 인데 칸이 16개뿐이라
**한 칸이 4px** 이다. 같은 화면에서 주인공 스프라이트의 한 칸은 3px 이고,
그 안에 눈·어깨받이·칼자루가 다 들어간다. 아이콘에는 검의 코등이 하나 넣을 자리가 없었다.
34개를 늘어놓고 보니 실루엣만 있고 속이 빈 그림들이었다 —
채찍은 덩어리, 낫은 갈고리, 잎은 횃불, 날개는 쐐기였다.

### 왜 32칸 하나로 통일하지 않는가

픽셀 그림은 줄일 수가 없기 때문이다.

아이콘이 놓이는 자리는 두 종류다. 글자 옆(속성 표시 · 남은 시간 · 처치 수)은
화면에서 16px 이고, 카드와 제단은 64px 이다. 32칸짜리를 16px 자리에 놓으면
한 칸이 0.5px 이 되어 픽셀 재질이 통째로 사라진다 — 뭉갠 벡터 아이콘이 된다.

그래서 **두 벌을 두고 크기를 보고 고른다.**

| | 칸 | 단계 | 쓰는 자리 |
|---|---|---|---|
| `MENU_ICONS` | 16 | 5 | 글자 옆 (cell 2~3 · 화면 16px) |
| `MENU_ICONS_HI` | 32 | 7 | 카드 · 제단 (cell 4 이상 · 화면 32~64px) |

### 두 벌의 화면 크기는 정확히 같아야 한다

처음에는 각 벌이 알아서 `round(cell × 7 / 칸수)` 로 칸 크기를 정하게 뒀다.
그랬더니 `cell 6` 에서 16칸은 한 칸 3px(48px), 32칸은 한 칸 1px(32px) 이 되어
**같은 아이콘이 자리에 따라 커졌다 작아졌다** 했다.

고친 규칙: 16칸의 칸 크기를 먼저 정하고, 32칸은 **그 절반**을 쓴다.
절반이 정수로 떨어질 때(짝수일 때)만 32칸을 쓴다 — 칸 크기가 정수가 아니면
칸 사이에 실금이 생긴다. 홀수로 떨어지면 한 칸 올려 짝수로 맞춘다.
하필 그 자리(48px · 80px)가 큰 자리라, 거기서만 성긴 그림이 나오면 제일 눈에 띄기 때문이다.

### 단계를 5에서 7로

32칸은 면이 넓어진다. 밝은 면과 어두운 면 사이에 중간이 없으면
색종이를 오려 붙인 것처럼 보인다.

`0` 윤곽 · `1` 깊은그늘 · `2` 그늘 · `3` 몸통 · `4` 빛 · `5` 밝은빛 · `6` 광

음영을 매기는 방법도 바꿨다. 16칸에서는 '열린 이웃이 몇 개인가'로 정했는데,
32칸에서는 그 방식이 테두리 한 줄만 밝히고 안쪽을 통째로 평평하게 남긴다.
지금은 **그 방향으로 몸이 몇 칸 남았는가**를 재서 표면에서 안쪽으로 단계를 만든다.

### 이번에 틀린 것들

32칸이 되니 16칸에서 통하던 요령이 오히려 방해가 됐다.

- **성속(元素)** — 고리 안에 무엇을 넣어도 **조준경**이 됐다. 눈금을 빼도 그랬다.
  고리를 아주 버리고 변이 오목한 네갈래 별 하나로 갔다.
  성역·인장도 고리라 셋이 한 덩어리로 보이던 문제까지 같이 풀렸다.
- **날개** — 깃을 다섯 개 나란히 세우니 **갈퀴**가 됐다. 면을 만들어 뒷전을 파냈더니
  이번엔 **물고기**가 됐다. 날개는 한 점에서 부채처럼 벌어지는 깃의 모음이고,
  길이가 서로 달라야 '접힌 날개'로 읽힌다.
- **낫** — 네 번 고쳤다. 원에서 원을 빼는 방식(16칸에서 통했던 것)은
  날의 두께를 마음대로 못 준다. 자루 쪽이 두껍고 끝이 얇아야 낫인데
  그게 안 되니 계속 갈고리였다. 각도를 따라가며 두께를 직접 주는 쪽으로 바꿨다.
- **잎** — 축을 따라 두께를 더했더니 잎이 주먹만 해지고 줄기가 길어져 **횃불**이 됐다.
  잎은 원 두 개가 겹친 자리(베시카)다 — 그러면 양 끝이 저절로 뾰족해진다.
  곁맥은 셋이면 잎, 다섯이면 깃털이다.
- **반지** — 알과 띠 사이를 넓게 이었더니 **자물쇠**가 됐다. 목을 좁히고 구멍을 키워야 반지다.
  알도 뾰족하면 고깔이라, 윗면(테이블)을 깎아야 보석으로 읽힌다.
- **주머니** — 목을 곧게 세우니 **항아리**였다. 묶인 자리가 잘록하고 그 위가 다시
  벌어져야 주머니다.
- **종** — 사다리꼴로 그으니 **등잔**이었다. 종은 직선이 아니라 굽은 선이다.
- **부활** — 불사조로 그렸더니 이 크기에서는 **잔(盞)** 으로 읽혔다.
  '되살아남'은 형상보다 운동이라, 한 바퀴 돌아 제자리로 오는 화살로 바꿨다.
- **한 칸짜리 장식은 못 쓴다** — 구슬 둘레에 흩어지는 마력 점을 찍었더니
  `outline` 이 그 한 칸에도 윤곽을 둘러 구슬 옆의 때처럼 보였다.

만드는 곳: `art/make-icons-hi.js` (`node art/make-icons-hi.js` 로 붙여 넣을 표를 뱉는다).


## 35. 아이콘 3차 — 색이 모자랐던 것이지 칸이 모자랐던 게 아니다

칸을 32개로 올린 다음에도 제보가 왔다. **"픽셀 색깔 수도 대폭 늘려서 세밀하고 미려하게 그려줘."**

이번에도 맞는 말이었고, 이번에는 원인이 더 근본적이었다.

`pxPal` 은 색 하나에서 세 단계를 뽑아 준다. 아이콘은 거기에 두 단계를 더해 일곱을 썼다.
**전부 한 가지 색조의 명암**이었다는 뜻이다. 검도 파랗고, 물약도 파랗고, 해골도 파랗다.
칸을 아무리 늘려도 강철과 나무와 금이 같은 색이면 세밀해 보이지 않는다.
32칸으로 올렸을 때 "더 나아지긴 했는데 여전히 밋밋하다"고 느껴진 이유가 이것이었다.

### 밝기 대신 재질을 적는다

칸마다 적는 값을 '몇 번째 밝기'가 아니라 **'무엇으로 만들어졌는가'** 로 바꿨다.

| 문자 | 재질 | 단계 |
|---|---|---|
| `0`~`7` | 호출 색 (속성색·직업색) | 8 |
| `a`~`e` | 강철 | 5 |
| `f`~`i` | 나무·가죽 | 4 |
| `j`~`m` | 금 | 4 |
| `n`~`q` | 뼈·돌 | 4 |
| `r`~`t` | 피 | 3 |
| `u`~`w` | 풀빛 | 3 |
| `x` `z` | 윤곽 · 순백 광점 | 2 |

**한 아이콘에 서른세 색.** 예전엔 일곱이었다.

호출 색을 완전히 버리지 않은 이유: 속성 표시(불·냉기·번개·피)와 조합 칸은
**색 자체가 정보**다. 그래서 '색이 뜻인 부분'만 `0`~`7` 로 두고 나머지를 재질로 굳혔다.
검은 어떤 색으로 불러도 강철이고 손잡이는 가죽이고 코등이는 금이지만,
불꽃과 마력탄과 보석은 부르는 색을 따른다.

### 음영은 자기 램프 안에서만 움직인다

`shade` 는 예전처럼 '그 방향으로 몸이 몇 칸 남았는가'로 단계를 정하되,
그 단계를 **칸이 속한 램프 안에서만** 옮긴다. 강철이 밝아져도 강철이어야 하기 때문이다.
그리고 각 램프의 `base` 문자만 건드린다 — 손으로 찍은 하이라이트를 나중에 지우지 않으려고.

### 성능

문자 종류가 서른셋이 되면서, 아이콘 하나를 칠할 때마다 32×32 를 서른세 번 훑게 됐다.
`iconPlan` 이 '문자 → 칸 목록'을 아이콘마다 한 번만 만들어 두고 그 뒤로 재사용한다
(WeakMap. 표 자체가 상수라 키가 안정적이다).

### 이번에 틀린 것

- **낫의 날 등이 하얗게 얼룩졌다.** 처음엔 표본이 모자라 점선이 되는 줄 알고
  120개에서 400개로 늘렸는데 그대로였다. 원인이 표본이 아니었다 —
  **손으로 찍은 칸과 `shade` 가 밝힌 칸이 한 줄에 섞여서**였다.
  굽은 면의 음영은 `shade` 에 맡기고 손을 뗐다. 안쪽 날만 한 줄 남겨 베는 쪽을 표시한다.
- **날개의 깃 넷이 붙어 종잇조각이 됐다.** 셋으로 줄이고 사이를 벌렸다 —
  비워 두면 `outline` 이 그 틈에 어두운 금을 그어 깃이 갈라져 보인다.

### 16칸 한 벌은 그대로 둔다

글자 옆(화면 16px)에서는 한 칸이 1px 이라 금 코등이가 1픽셀이 된다. 의미가 없다.
작은 자리는 계속 호출 색의 단색 배지로 두고, 큰 자리만 재질로 칠한다.

## 36. 주인공 — 재질을 여기에도

아이콘을 재질로 다시 그리고 나니 같은 지적이 주인공에게도 왔다.
**"주인공 캐릭터도 픽셀 색깔 수도 대폭 늘려서 세밀하고 미려하게 그려줘."**

주인공은 이미 64칸에 직접 그려져 있었고, 단색이 아니라 살·강철·가죽을 나눠 쓰고 있었다.
그런데도 멀리서 보면 **흰 갑옷에 노란 십자 하나**였다. 세어 보니 이유가 나왔다.

| | 예전 | 지금 |
|---|---|---|
| 살 | 2단계 | **4단계** (`y s S Y`) |
| 강철 | 3단계 | **5단계** (`e m M H X`) |
| 가죽 | 4단계 | **5단계** (`d l L u U`) |
| 직업색 | 3단계 | **5단계** (`t a A G T`) |
| 금 | 없음 | **4단계** (`j J o Z`) |
| 붉은 안감 | 없음 | **3단계** (`h i I`) |
| 검은 무쇠 | 없음 | `b` |
| 뼈 | (보스 전용) | 전사의 뿔에 씀 (`E F`) |

주인공 한 명에 **서른 색**이 오른다. 팔레트 글자는 31개가 됐다.

### 무엇에 썼나

- **금은 테두리로만.** 가슴판 윗단, 투구 이마띠, 허리 버클, 코등이, 자루 끝, 방패 테두리.
- **망토에 붉은 안감.** 겉감 한 색이면 천이 아니라 판이다. 몸 쪽으로 접힌 면에
  붉은 줄을 한 줄 넣으면 '뒤집힌 천'으로 읽힌다. 금 옆에 붉은 게 있어야 갑옷이 산다.
- **전사의 뿔을 뼈로.** 강철로 두면 투구와 한 덩어리가 된다.
  뼈는 이 화면에서 유일한 중립색이라, 그것만으로 뿔이 떨어져 나온다.
- **마법사 로브에 금 자수 밑단.** 한 색으로 떨어지면 목욕가운이다.
  단이 있어야 '지어 입은 옷'이 된다.
- **마법사 수염을 상아로.** 강철색이면 얼굴 밑에 판을 댄 것 같다. 상아가 따뜻해서 털로 읽힌다.
- **사슬은 어두운 자리와 밝은 자리를 붙여서.** 어두운 점 하나만 찍으면 32px 에서는 얼룩이다.

### 여기서 한 번 틀렸다

**성기사가 통째로 금덩이가 됐다.** 가슴 십자를 5칸 폭으로, 방패 십자를 두껍게 칠했더니
갑옷·망토·십자가 전부 금빛으로 붙어 버렸다 — 성기사의 직업색이 애초에 금빛이라
금을 넓게 쓰면 안 되는 것이었다.

금은 **테두리로만** 쓰고 넓은 면은 흰 강철로 두었다. 대비는 망토 안감의 붉은색이 맡는다.

### 한 가지 더 — `s` 를 건드리면 주인공만 바뀌지 않는다

팔레트는 스프라이트 전체가 함께 쓴다. 살 그늘 `s` 를 4단계 램프에 맞추느라
`#c49a72` 에서 `#c99b74` 로 반 단계 올렸는데, 이 글자는 주인공 말고도 쓰인다.
색을 고칠 때는 그 글자를 누가 쓰는지부터 봐야 한다.

## 37. 몬스터 — 색이 모자랐던 게 아니라 안 쓰고 있었다

주인공을 재질로 다시 칠하고 나서 몬스터 차례가 됐다.
그런데 팔레트를 열어 보니 놀라운 것이 있었다.

**몹의 몸색은 처음부터 여덟 단계가 있었다.** `t · c · a · D · B · C · G · T` —
바탕색 하나에서 -.68 부터 +.84 까지. 그런데 몹 실루엣은 그중 **넷(c·D·B·C)** 만 쓰고 있었다.
색이 모자랐던 게 아니라 있는 색을 안 쓰고 있었던 것이다.

거기에 재질을 들였다. 주인공용으로 만든 강철·가죽·금·뼈·피가 이미 팔레트에 있었으니
새로 만든 것은 **녹슨 쇠 둘(`w` `x`)** 뿐이다.

> 강철(`M m e`)은 차가운 회색이라 주인공 갑옷의 색이다.
> 족쇄·목줄·화살촉처럼 **버려진 쇠**는 따뜻하게 삭아야 한다.

### 무엇을 붙였나

| 몹 | 붙인 것 |
|---|---|
| 슬라임 | 삼킨 **금화** · 삼킨 **녹슨 조각** · 테두리에 도는 빛 · 아래로 4단계 투과광 |
| 박쥐 | 막의 **뼈 손가락** · 막 끝에 비치는 **핏빛** · 귀 안쪽과 주둥이 **살빛** |
| 유령·사신·주술사 | 두건 속의 **뼈 얼굴** · 삐져나온 뼈 손가락 · 허리의 **녹슨 사슬** |
| 좀비 | 드러난 **갈비뼈** · 뚫린 배와 **마른 피** · 걸친 **가죽 넝마** |
| 거구 | 어깨를 가로지르는 **가죽띠**와 **쇠못** · 가슴의 상처 |
| 궁수 | **나무 활** · **가죽 화살통** · 쇠촉 화살 · 뼈 깃 · 시위 |
| 돌격병 | **녹슨 뿔투구** · 뼈 뿔 · **코뚜레** |
| 방패병 | **강철 방패**에 **금 십자**와 보스 · 강철 투구 · 녹슨 못 |
| 사냥개 | **목줄**과 쇠징 · 뼈 발톱 · 핏빛 눈 · 귀 안쪽 살빛 |
| 보스 | 허리의 **금단과 버클** · 어깨 갑판의 금단 · 뿔 밑동의 **금관** · 망토의 **붉은 안감** |

두 가지가 특히 크게 달라졌다.

**유령의 두건 속.** 구멍만 두면 '얼굴 없음'에서 멈춘다. 그 안에 뼈 얼굴을 반쯤 띄우니
'얼굴이 없는 게 아니라 남은 게 뼈뿐'이 됐다.

**사냥개의 목줄.** 짐승에 사람이 채운 물건이 하나 붙으면 '야생'이 아니라 '풀려난 것'이 된다.
같은 실루엣이 훨씬 사납게 읽힌다.

### 이번에 틀린 것

- **사냥개 얼굴이 분홍 덩어리가 됐다.** 눈을 4칸 폭으로 붉게 뒀더니 귀 안쪽의 살빛과
  합쳐졌다. 짐승의 눈은 작고 깊어야 사납다 — 좁히고 둘레를 어둡게 팠다.
- **좀비의 상처가 주머니처럼 네모났다.** 사각형으로 뚫었기 때문이다. 타원으로 바꾸고
  아래로 흘러내린 자국을 두 칸 찍었다.
